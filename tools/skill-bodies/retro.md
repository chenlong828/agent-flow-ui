## 适用场景

一个非平凡问题已经解决并验证，你要把这次过程变成可复用的资产：一份结构化学习文档，加若干条针对流程、脚本、技能的改进项。目标是下一次遇到同类问题时，查一下就能省下研究时间。

输入：一次已完成的排查或修复（对话轨迹、命令与退出码、命中的技能与脚本、阶段与门控记录）、根因结论、验证证据。输出：学习文档（带 frontmatter，可检索）、复盘结论（事实与推断分层）、改进项清单（含落地方式与状态）。

触发词：复盘、沉淀、经验固化、学习文档、root cause、改进项、资产健康。

不适用：问题还没解决；只是 typo 或显而易见的错；需要检索已有学习（那是读端，不是本技能）。

## 执行步骤

### 第一步：判是否值得沉淀

三个前置条件同时满足才写：

1. 问题已解决，不是进行中。
2. 解法已验证，有可复核的证据。
3. 问题非平凡，不是拼写错误、配置漏填这类看一眼就会的。

任一不满足：交互模式下询问是否仍要记录；无人值守模式下输出「跳过 + 原因」，不硬写。

### 第二步：确定复盘对象与证据

复盘只针对这次实际用过的东西，不泛化到整个资产库：

| 类别 | 对象 | 证据来源 |
|---|---|---|
| 技能 | 本次加载并实际使用的技能 | 加载记录与引用痕迹 |
| 脚本 | 卡内或编排调用的工具脚本 | 命令、参数、退出码 |
| 流程 | 阶段、门控、专家卡 | 阶段执行与门控记录 |

每类逐项对照判据，命中才产出一条改进候选。候选必须附本案的证据锚：文件与行号、字段、命令输出。没有证据锚的候选无效，不凭印象写。

技能类有一个豁免口径：专家卡没有技能列，或本次运行零技能调用，则不产候选，只在覆盖说明里记一行「技能类：无技能列 / 无调用痕迹，豁免」。但脚本类与流程类照常判；如果卡里有技能列却一次没调用，记一条观察项，提示这列该删还是该真正加载。

### 第三步：把根因说清

复盘的重点不是「谁错了」，是「为什么这样能解、为什么之前没解」：

- 直接原因：现象由哪个具体行为触发。
- 根因：机制层面为什么允许这个行为发生。
- 为什么之前没发现：是检测缺失、覆盖缺失，还是知识缺失。
- 为什么现在能解：本次哪一步、哪个证据起了决定作用。

事实与推断分开写。事实标 verified，附证据；推断标 inferred，写清依据与不确定点。两者混在一起，复盘就会变成故事。

### 第四步：写学习文档

学习文档按固定结构写，放知识库的解决方案目录，按分类归档。文件名用问题 slug，不加日期后缀，日期放 frontmatter。

frontmatter 至少包含：标题、分类、问题类型、组件、严重度、创建时间、最后更新时间、标签。字段值要能被检索到，标签用业务词与技术词各一两个，不要堆一长串。

正文按轨道选模板：

- 缺陷轨：问题现象、影响范围、根因、解法、验证证据、预防措施。
- 知识轨：背景、结论、适用条件、反例、参考。

写之前先查重：在解决方案目录检索同主题旧文档，按标题、标签、模块三个维度并行搜，只读 frontmatter 打分。

| 重叠度 | 动作 |
|---|---|
| 高（同问题、同根因、同解法） | 更新旧文档，补新证据与预防，刷新最后更新时间，保留原路径与标题 |
| 中（同区域、不同角度） | 新建，标注可能需要合并 |
| 低或无 | 新建 |

写完跑校验：frontmatter 字段齐全、必填项非空、数组项引用安全。校验退出码为 0 才算完成；不为 0 按提示修正后重跑，不宣布成功。

### 第五步：改进项落地

改进项不是写完就算，要给落地路径与状态：

| 处置 | 适用 | 谁执行 |
|---|---|---|
| 自动落地 | 脚本类，有回归护栏 | 自动改，事后抽查 |
| 内容增补 | 技能文档补规则 | 自动改，事后审 |
| 人工事前 | 流程、门控、结构性规则 | 人工评审后改 |
| 转工单 | 知识缺失、工具缺陷 | 转对应负责人 |
| 观察 | 暂不确定是否要改 | 记录，下轮再看 |

状态闭环：候选 → 确认或驳回 → 已落地 → 已归档。驳回要写理由；落地要写清改前版本与改后版本，并回链到本案。

### 第六步：归档与复查

复盘产物双写：一份放本次任务的复盘目录，一份放归档区。归档后不再改写；后续修正用新增条目表达，不覆盖历史。

除锈（复查旧学习）只在两种情况下做：新结论推翻或取代了旧学习；本次重构、迁移、重命名导致旧文档引用失效。复查必须带窄范围（文件名、模块或分类），禁止无范围全量扫。

### 学习文档骨架

```yaml
---
title: 一句话说清问题与解法
category: 缺陷 / 知识
problem_type: 空值 / 并发 / 配置 / 契约
component: 模块或服务
severity: P0 / P1 / P2 / P3
tags: [业务词, 技术词]
created: YYYY-MM-DD
last_updated: YYYY-MM-DD
---
```

正文按轨道写：

- 缺陷轨：现象、影响、根因、解法、验证、预防。
- 知识轨：背景、结论、适用条件、反例、参考。

标题用「问题 + 解法」的说法，不用「关于……的总结」。标签控制在四个以内，多了等于没有标签。

### 状态流转

| 状态 | 含义 | 谁能改 |
|---|---|---|
| candidate | 自动复盘产出的候选 | 复盘流程 |
| confirmed | 人工确报 | 坐席签字 |
| rejected | 驳回，附理由 | 坐席 |
| landed | 已落地，附版本变化 | 执行人 |
| archived | 已归档，不再改写 | 归档流程 |

状态只能向前，不回退；需要修正时新增一条记录并引用原条目。驳回不等于删除，理由要能被后续复盘检索到。

## 示例

**示例一：一次接口超时排查**

轨迹显示：先查日志未命中，后按功能号定位到下游调用，发现连接池配置过小。根因是配置项未随并发上调。学习文档写缺陷轨：现象、影响、根因、解法、验证（压测前后耗时对比）、预防（连接池容量纳入上线检查）。改进项两条：上线检查清单加一项（人工事前）；监控加连接池使用率告警（转工单）。两条都有证据锚与状态。

**示例二：脚本哑火**

复盘发现某检索脚本因参数变化静默返回空结果，导致排查多花两小时。改进项：脚本加参数校验与空结果显式报错（自动落地 + 回归护栏）；技能文档补一句「空结果先验参数」（内容增补）。候选附命令与退出码证据。

**示例三：零技能调用**

本次运行专家卡有技能列，但一次没加载。按豁免口径不逐条报技能问题，只记一条观察项：确认该列是否该删，或加载条件是否写错。脚本类与流程类照常产出候选。

## 脚本

无脚本。产物为 Markdown 学习文档与复盘结论；frontmatter 校验由调用方的校验器执行，退出码为 0 才算通过。

## 完成验证

- [ ] 三个前置条件满足，或已记录跳过原因。
- [ ] 复盘对象限定为本次实际使用的技能、脚本、流程。
- [ ] 每条候选有证据锚，事实与推断已分层。
- [ ] 根因回答了「为什么之前没发现、为什么现在能解」。
- [ ] 学习文档 frontmatter 齐全，查重后新建或更新。
- [ ] 校验退出码为 0。
- [ ] 改进项有处置方式与状态，落地记录含版本变化。

## 常见踩坑

- **问题没解决就沉淀**：把进行中的猜测写成结论，下一次会被误导。先解决再写。
- **候选没有证据**：凭印象说「技能不好用」，无法复核也无法落地。每条都要锚。
- **事实与推断混写**：推断写得像事实，复盘可信度归零。分层标注。
- **同主题重复新建**：不查重就写，知识库越积越乱。高重叠必须更新旧文档。
- **校验不过宣布成功**：frontmatter 不合法，后续检索不到，等于没写。
- **改进项只写不改**：没有责任人与状态，复盘变成作文。
- **无范围除锈**：全量复查耗时且容易误删，必须窄范围。
