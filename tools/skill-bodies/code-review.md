## 适用场景

你拿到的是一个分支相对基线的改动，要在合并或提测前判断它能不能进。本技能把判断拆成动作：定范围、组建评审团、各评审者并行看一遍、合并去重、逐条过置信度门、独立复核，最后给出带证据的结论。

触发场景：合并前检查、提测前检查、让模型 review 本次改动、流水线向集成阶段交接时由编排器调用、抽样巡检复用同一套格式。触发词：代码评审、review 代码、合并前评审、提测前检查、多角色评审、置信度门控、发现去重。

不适用：设计文档与交付物评审走文档评审门；全仓抽样巡检只复用评审者定义与发现契约；单纯跑静态检查工具不构成本技能；范围不可确定时直接失败，不要"尽力评审"。

只评审不推送：不 push、不开合并请求、不切分支、不改被评审分支。默认模式可应用确定的安全修复并跑验证，验证失败就回退改为报告；被编排调用时只输出报告，放行由调用方决定。

与人工评审的分工。本技能管机械化的穷举与证据固定：diff 每处都过、每条发现带位置证据与定级、去重与抑制成可重复规则、结论可追溯。人工管替代不了的判断：业务意图的最终确认、架构取舍、跨团队契约协商、发布节奏，以及所有责任人为人工的条目。交接时交出人工待决项、残留风险与测试缺口，不代替人放行；推翻定级要写明原因，否则置信锚会漂移。

## 执行步骤

### 一、确定范围与意图

判据：调用方显式给了基线就按给定的解析，没给就取当前分支相对默认分支的合并基点（`git merge-base HEAD <ref>`）。做法：取 `git diff --name-only $BASE` 的文件列表、`git diff -U10 $BASE` 的 diff、`git ls-files` 列出的未跟踪文件；上下文取 U10 而非 U3，因为判断周边是否已处理需要函数体级上下文。未跟踪文件默认不评审，但在覆盖说明里单列。反例：解析不出基线就退化成 `git diff HEAD`，漏掉已提交工作，范围变空、结论变成没问题。

范围定好后读 `git log --oneline $BASE..HEAD` 与对话上下文，写两三行意图摘要传给每个评审者。意图只影响看多深，不影响选谁；提交信息写了"重构"就跳过安全评审者，等于用作者自述替代判断。

### 二、组建评审团

| 评审者 | 常驻 | 职责边界 | 触发判据 |
|---|---|---|---|
| 正确性 | 是 | 逻辑错误、边界、状态 bug、空值异常、并发时序 | 无条件 |
| 可维护性 | 是 | 耦合、复杂度、命名、死代码、重复、类型泄漏 | 无条件 |
| 项目规范 | 是 | 只对照成文规则与目录约定，不发明规则 | 无条件 |
| 测试 | 是 | 覆盖缺口、弱断言、缺回归测试与执行日志 | 无条件 |
| 经验检索 | 是 | 检索经验库命中的过往问题，单独综合 | 无条件 |
| 安全 | 否 | 鉴权、对外接口、用户输入、权限、敏感数据 | 进入这类风险的触发面 |
| 性能 | 否 | 数据库查询、大数据转换、缓存、异步、循环内 IO | 改变这些路径的复杂度或次数 |
| 接口契约 | 否 | 序列化、出入参结构、版本化、破坏性变更 | 触及对外结构 |
| 前端响应式 | 否 | 响应式丢失、生命周期时序、侦听副作用、异步竞态 | 触及前端组件 |
| 后端语言 | 否 | 并发安全、事务边界、资源未关闭、空指针、异常吞没 | 触及后端代码 |
| 数据库 | 否 | 缺索引、全表扫描、锁、迁移安全、时区裸写法 | 触及 DDL、DML、索引、SQL |

经验检索是已注册子 agent，直接派发；其余评审者用通用子 agent 注入提示词实现。职责边界要守住：正确性不评价命名，可维护性不判安全漏洞，项目规范只引用成文规则；重叠区域（循环里查库既像性能又像可维护性）由触发判据定归属，两边都报时留到合并阶段按指纹处理。

规模：小配置改动零条件共五人；带大列表渲染的前端页面改动可能加响应式与性能共七人；只改文档时跳过运行时导向的评审者。判断依据是改动行为是否落在那类风险的触发面上，不做关键词匹配；出现 token 就当安全问题、出现 select 就当数据库问题，注释里出现也会误触发。派单前公布评审团并说明理由，不是等确认。

### 三、并行派发

判据：每人拿到同样的范围材料，但只拿自己那份职责定义，避免视角互相污染。做法：取 run-id、建产物目录，把职责定义、发现字段契约、意图摘要、文件列表、diff、范围说明六样注入提示词。只读约束写进提示词：可读文件、可检索、可跑只读 git 命令，禁止写文件、提交、推送。反例：把全部定义塞给一个子 agent 同时从六个角度评审，每一面都只看一层。

返回分两层：合并层回给编排者，只装判断与排序要用的字段；详情层落产物文件，字段归属见脚本一节。并发有上限，排队不算失败；正确性与安全继承会话模型，其余可用小模型降本。

### 四、发现字段契约

每条发现必须满足下表字段，缺字段或越界值在合并阶段直接丢弃。

| 字段 | 取值 | 判据与做法 |
|---|---|---|
| 标题 | 短句 | 十二字内说清问题，不写"代码质量有问题" |
| 严重度 | P0 至 P3 | 按影响面定级，风格瑕疵不能标 P0 |
| 文件 | 仓库根相对路径 | 与 diff 路径一致，不写绝对路径 |
| 行号 | 大于零整数 | 指改动后的实际行，不用 diff 相对行 |
| 影响说明 | 字符串 | 写会坏什么、失败模式，不复述代码 |
| 证据 | 至少一条 | 片段、行引用、模式描述，能独立核对 |
| 置信度 | 0、25、50、75、100 | 五档枚举，不写 60 或 80 |
| 修复建议 | 字符串或空 | 可辩护的最小修复，不写"建议重构" |
| 修复类别 | 自动可修、需人工、仅报告 | 后续工作形态信号，不是应用门控 |
| 责任人 | 下游处理、人工、发布 | 按谁收口判定，不一律归下游 |
| 需复验 | 布尔 | 修复后是否要定向测试或复审 |
| 既存 | 布尔 | 本次 diff 之外早已存在为真 |

置信锚决定一条发现能否进报告：0 是假阳或既存，不进合并；25 是存疑无法验证；50 是已验证但次要或纯风格；75 是确认会影响用户或运行时；100 可从代码直接证实，例如编译错、确定逻辑 bug、可引用的成文规范违反。

| 级别 | 判据 | 处置 |
|---|---|---|
| P0 | 关键破坏、可利用漏洞、数据丢失 | 合并前必修 |
| P1 | 正常使用会命中的高影响缺陷、破坏契约 | 应修 |
| P2 | 中等问题：边界、性能回退、可维护性陷阱 | 顺手则修 |
| P3 | 低影响、范围窄、小改进 | 由用户自定 |

反例：注入漏洞标成 P3、命名风格标成 P0，前者让真问题漏出，后者让报告失去可信度。

### 五、合并与门控

合并按固定顺序执行，顺序本身是规则的一部分。

一、校验。丢弃缺字段或越界值的发现并计数；置信度写 60 就整条丢弃，不四舍五入替评审者改自评。

二、去重。指纹取规范化路径、行号上下三行的桶、规范化标题；命中则合并，严重度与锚各取高，记录命中的评审者。按整段文字比对会漏掉措辞不同的同一缺陷。

三、跨员晋级。两个以上独立评审者命中同一指纹，锚升一档（50 到 75，75 到 100），评审者列标注来源；同一人报两次不算独立。

四、分离既存。既存为真的单列，不计入判定，但保留在报告里便于排期。

五、弱信号降级。低严重度、仅报告、且只由测试或可维护性贡献的发现，移到测试缺口或残留风险。

六、置信门控。在以上步骤之后执行，抑制锚低于 75 的发现，例外是 P0 且锚不低于 50 必须保留，并记录各锚抑制数。先门控再晋级会掐掉本该被第二人印证、晋到 75 的发现，报告表面还看不出顺序错误。

七、路由。定修复类别与责任人，拿不准取保守方向：不确定能否自动修归需人工，不确定谁收口归人工。

八、排序编号。P0 在前，再按锚降序、路径、行号，全局单调，下发后不再变动。

### 六、独立复核

判据：合并后的发现仍出自单个评审者，可能夹带浅读假阳。做法：给每条存活发现派独立上下文的复核子 agent，提供标题、严重度、文件、行号、修复建议与 diff，只问是否成立与理由。判否即丢弃并记原因；P0 与 P1 遇复核本身失败时不丢弃，标降级交人工；存活超十五条按严重度取前十五。反例：让原评审者自己复核，浅读盲区原样复现。

### 七、结论与输出

三档：通过、有条件通过、驳回，对应可以合并、修复后可合并、不可合并。

- 通过：无 P0 与 P1，P2 与 P3 均仅报告或已应用并通过验证。
- 有条件通过：有 P0 或 P1，但每条都有可执行修复建议或明确人工动作，且不涉及架构取舍；写清修哪几条、修完怎么验。
- 驳回：有 P0 且提不出可辩护的最小修复，或发现指向设计层问题需重新决策，或范围不可评审。

反例：有一条 P2 就驳回会让评审退化成噪声源；把存在 P0 写成有条件通过并解释"来得及修"，等于把放行责任推给时间。

默认模式输出中文 markdown，按 ASCII 安全处理，不用箭头字符，管道表格不用制表符画线：头部写范围、意图、评审团及理由；已应用修复附验证结果；发现按严重度分组的管道表格加键控行详情；既存问题单列；覆盖说明写抑制数、降级数、复核丢弃数及原因；最后结论。

被编排调用时输出单个裸 JSON 对象，无围栏，对象后不写文字，同时落一份到产物目录；JSON 前后加说明文字会让编排器解析失败。

## 示例

**并行：前端列表页改动。** 改动换了筛选、加了轮询、一次渲染五百行。按触发判据组队：四位常驻加经验检索，叠加响应式与性能，共七人并行派发。正确性报 P1（轮询定时器在组件卸载后未清理，锚 75），响应式报 P1（解构 props 导致响应式丢失，锚 75），性能报 P2（每次筛选全量重排，锚 50），测试报 P2 仅报告（缺回归断言，锚 50），按弱信号降级移到测试缺口。门控后存活两条 P1，复核通过，结论为有条件通过，放行条件写明修掉两处并各补一条回归断言。

**去重与定级：事务未回滚。** 正确性与后端语言报了同一处：异常分支里事务没回滚，措辞不同，行号差两行。指纹按路径、行号桶、标题规范化后一致，合并成一条，严重度取高为 P1，锚两个 50 取高仍是 50；命中来自两个独立评审者，执行跨员晋级，锚升到 75，刚好越过后置门控，评审者列记为正确性加后端语言。不做去重会出现两条同位置 P1 且建议冲突；晋级若排在门控之后，这条锚 50 的 P1 会被抑制，两人独立看到的问题就漏掉了。

**误报驳回：空指针与越界值。** 某评审者报"可能存在空指针"，锚 25，证据只写文件路径、没有片段。复核子 agent 拿到 diff 后确认上游已判空并返回默认值，失败路径到不了该行，返回否并写明理由，这条丢弃。同批另有两条被丢弃：缩进不一致属静态检查工具范围；置信度写成 60 不在五档内，按越界值整条丢弃并计数。三条都记进覆盖说明，报告里不出现但原因可查。存活发现里有一条 P0 提不出可辩护的最小修复，结论定为驳回，责任人记人工。

## 脚本

无脚本。本技能不调用外部命令做评审判断，只用 git 只读命令确定范围与取 diff；评审者是只读子 agent，派发这一步是注入提示词。

注入六项缺一不可：职责定义与边界、发现字段契约、意图摘要、文件列表、U10 上下文的 diff、范围说明（哪些不评审、未跟踪文件清单）。最常见的是漏掉职责边界，导致多个评审者报同一类问题。

| 字段 | 层级 | 说明 |
|---|---|---|
| reviewer、findings、residual_risks、testing_gaps | 合并层顶层 | 评审者名、发现数组、无法确认的风险、测试缺口 |
| title、severity、file、line、confidence、autofix_class、owner、requires_verification、pre_existing | 合并层 | 判断、排序、路由所需 |
| suggested_fix | 合并层，可省略 | 由调用方决定是否带下来 |
| why_it_matters、evidence | 详情层 | 落产物文件，紧凑返回省略 |

编排者最终产物字段：状态、结论、范围（基点、分支、变更文件数）、意图、评审者列表、发现、可执行发现、既存发现、已知模式、残留风险、测试缺口、覆盖说明、产物目录、run-id。失败只输出状态与原因。

格式约束：单个裸对象、无代码围栏、对象后无文字；另需落一份到产物目录供事后追查。

## 完成验证

- [ ] 范围来自合并基点，未退化成对工作区取 diff，未跟踪文件已列出。
- [ ] 意图摘要写在报告头部，且未用于挑选评审者。
- [ ] 每条发现的十二个字段齐全，置信度落在五档之内。
- [ ] 去重指纹按路径、行号桶、标题三项计算，跨员晋级已执行并标注来源。
- [ ] 门控发生在晋级与降级之后，例外只对 P0 且锚不低于 50 生效。
- [ ] 既存发现单列，未计入结论判定。
- [ ] 复核对每条存活发现给出成立与否及理由，P0 与 P1 未被无故丢弃。
- [ ] 结论是三档之一，有条件通过写清修哪几条、修完怎么验。
- [ ] 覆盖说明含抑制数、降级数、复核丢弃数、残留风险、测试缺口。

## 常见踩坑

- **基线解析失败就退化取 diff**：`git diff HEAD` 漏掉已提交工作，范围变空还给通过结论。应直接失败并报出原因。
- **先门控后晋级**：抑制阈值低于晋级后的锚，会掐掉两个评审者独立命中的问题。门控必须在去重、晋级、降级之后执行。
- **按整段文字去重**：措辞不同就漏合并，同位置留两条冲突发现。指纹只取路径、行号桶、标题。
- **浅读假阳**：看到可疑就报，没确认周边是否已处理。复核专为这类问题设，更省成本的是评审者自己先读上下文。
- **报告静态检查能抓的问题**：缩进、分号、未使用变量重复报，稀释真问题，报告长到没人读。
- **用关键词选评审者**：注释里出现 token 就拉安全、出现 select 就拉数据库，人来了找不到可报内容。判据应是改动行为是否落在触发面上。
- **评审者越界**：可维护性去判安全漏洞、项目规范去发明规则，越界发现质量低还挤占真问题编号。
- **意图不明就停下问人**：一次评审阻塞整条流水线。应尽力推断，把不确定写进覆盖说明。
- **有条件通过写成模糊放行**：只写"建议修复后合并"，没写修哪几条、怎么验，等于把判断退回给下一个人。
- **既存问题计入结论**：祖传缺陷把结论拖成驳回，改动作者无法处理，报告随之失去约束力。
