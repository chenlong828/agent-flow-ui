## 适用场景

接口改了或新加了，你要用断言确认「说好的契约」和「实际返回」一致。契约断言的依据是接口契约文档、schema 或设计说明，不是实现代码；实现怎么写不影响契约该是什么。

输入：接口标识、契约版本、可用环境与测试数据。输出：断言清单与执行结果，失败项带请求、响应与契约条款位置。

触发词：契约断言、接口校验、schema 校验、返回结构、字段类型、错误码、兼容性。

不适用：业务逻辑正确性（那要用例断言）；性能压测；页面展示验证。

## 执行步骤

### 第一步：取契约并锁定版本

先拿到契约的权威来源：接口文档、OpenAPI/Swagger、JSON Schema、设计评审结论。记录版本与获取时间；没有版本的契约不可作为断言依据。

契约与实现冲突时，以契约为准，把冲突登记为问题，不按实现改断言。契约本身缺失或含糊时，先补契约再断言，不猜字段含义。

### 第二步：列断言清单

按维度列，不要只测「能不能调通」：

| 维度 | 断言内容 | 失败示例 |
|---|---|---|
| 状态码 | 成功、参数错误、未授权、不存在、冲突各自的码 | 参数错误返回 500 |
| 结构 | 必填字段存在，层级正确，数组元素结构一致 | 少返回 `data.items` |
| 类型 | 字符串、数字、布尔、日期格式 | 金额返回字符串 |
| 枚举 | 状态、类型取值在约定集合内 | 返回未定义的 `status=9` |
| 空值与缺省 | 可空字段显式返回 null，不可空字段不缺失 | 可空字段直接消失 |
| 错误体 | 错误码、错误信息、追踪号结构一致 | 错误只返回一段文本 |
| 分页 | 页码、页大小、总数、has_more 语义一致 | 总数与实际条数不符 |
| 幂等 | 重复提交结果一致，副作用只发生一次 | 重复提交生成两条记录 |
| 兼容 | 新增字段不破坏旧客户端；删除字段有过渡期 | 直接删字段导致旧页面白屏 |

每条断言写清：接口、场景、期望值、契约出处。没有出处的期望值是个人偏好，不进清单。

### 第三步：设计正例与反例

正例覆盖主流程：最小必填、全字段、边界值。反例覆盖拒绝路径：缺必填、类型错、枚举越界、超长、越权、重复提交。

反例的期望必须来自契约：契约写了返回哪个错误码，就断言哪个；契约没写，只断言「被拒绝且错误体结构合法」，不写死具体码。

### 第四步：执行与取证

每个断言记录四样：请求（方法、路径、关键参数）、响应（状态码、关键字段）、契约出处、判定结果。失败时保留完整响应体与追踪号，便于定位是实现问题还是契约问题。

同一接口的多条断言合并成一次执行，减少重复调用；但失败定位要精确到断言项，不能只报「接口失败」。

### 第五步：判定与交接

结果分三类：

- 通过：全部断言满足。
- 契约不一致：实现与契约冲突。交实现方修，或走契约变更流程，二选一，不能既不修也不改契约。
- 契约缺失：断言无法判定。登记缺口，补契约后重跑。

契约变更必须评估兼容性：新增可选字段通常兼容；改字段类型、删字段、改枚举语义不兼容，需要版本或过渡期。兼容性结论写进报告，不默默上线。

### 第六步：版本与兼容性

契约变更按兼容性分三档，处理方式不同：

| 变更 | 兼容性 | 处理 |
|---|---|---|
| 新增可选字段 | 兼容 | 直接发，旧客户端忽略 |
| 新增必填入参 | 不兼容 | 给默认值，或升版本 |
| 字段改类型 | 不兼容 | 升版本，保留旧字段过渡 |
| 删除字段 | 不兼容 | 先标记废弃，观察一个周期再删 |
| 改枚举语义 | 不兼容 | 新增枚举值而非改旧值含义 |
| 改错误码 | 视调用方 | 同步通知，旧码保留映射 |
| 改默认值 | 隐性不兼容 | 评估调用方是否依赖默认 |

兼容性结论要写进报告，不能只在评审口头说。涉及不兼容变更时，明确版本号、过渡期、回滚方式。

### 第七步：失败处置

断言失败先分类，再决定谁修：

- 实现缺陷：返回与契约不符，交实现方修。
- 契约过期：文档没跟上实现，走契约更新流程，同时确认调用方影响。
- 环境问题：依赖不可用、数据缺失，修环境后重跑，不计入契约结论。
- 断言写错：期望值本身有误，修正断言并记录，不将错就错。

修完复跑只跑失败项与受影响项，不全量重跑；复跑结果附在报告后。

### 第八步：固化与回归

一次性的断言价值有限，稳定后要固化：断言清单入库存版本、纳入持续集成、每次接口变更自动跑受影响接口。

固化时给断言分级：P0 是主流程与契约核心，必跑；P1 是错误路径与兼容性；P2 是展示性字段。CI 只跑 P0，发版前跑 P0 与 P1。

契约变更时同步更新断言，避免「断言过期导致假失败」；连续失败的断言要复核是契约变了还是实现退化。

### 第九步：出报告

报告按接口分组，每组给：断言总数、通过数、失败数、失败明细、契约版本、环境与时间。失败明细一行一条，包含断言、期望、实际、契约出处、处置建议。

报告末尾给结论：全部通过、部分失败（列阻塞项）、契约缺失。结论要能直接被提测或发布流程消费，不写「基本没问题」。

## 示例

**示例一：新增返回字段**

契约新增可选字段 `rival_code`。断言：成功响应包含该字段；无值时返回 null 而不是缺失；旧字段不变。执行通过后，再验证旧版客户端不因新字段报错。

**示例二：错误码变更**

契约把「资金不足」从 500 改为 400 + 业务码 E1001。断言：状态码 400、错误体含 E1001、错误信息非空。实现仍返回 500 时判契约不一致，附请求与响应。

**示例三：分页语义**

契约约定 `total` 为满足条件的总条数，`items` 为当前页。断言：total 大于等于 items 长度；翻页后 items 不重复；最后一页 has_more 为 false。三条都过才算分页契约成立。

**示例四：不兼容变更**

契约要把 `amount` 从字符串改成数字。这是不兼容变更：新版本加 `amount_num` 数字字段，旧字段保留一个周期；断言同时校两个字段，并验证旧客户端不报错。报告里写清版本号、过渡期与回滚方式。

## 脚本

无脚本。断言可用接口测试工具或轻量脚本执行；核心是断言清单与契约出处一一对应，执行方式不影响判定。

## 常见踩坑

- **按实现写断言**：实现返回什么就断言什么，契约错了也发现不了。以契约为准。
- **只测 200**：状态码、错误体、分页、幂等都没覆盖，上线后问题成片。
- **期望值没有出处**：断言变成个人偏好，争论无法收敛。
- **可空字段当缺失**：契约说可空，实现直接不返回，前端取值报错。
- **契约变更不看兼容**：删字段、改类型不评估，旧客户端直接崩。
- **失败只报接口错**：不写哪条断言、什么期望、什么实际，定位成本高。
- **断言没有分级**：P0 和 P2 混在一起跑，CI 又慢又吵，最后没人看。
- **断言过期不维护**：契约改了断言没改，天天假失败，团队直接忽略告警。
- **只验成功响应**：错误体、分页、幂等都没断言，问题都留到线上。
