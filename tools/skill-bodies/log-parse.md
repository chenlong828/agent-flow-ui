## 适用场景

你拿到一批现场原始素材：日志目录或单份大日志、redo 段及其解析产物、报盘与前置机日志、T2 报文日志、功能号统计 CSV、todb 配置件。任务是把它们变成可复核的结构化证据，回答某时、某节点、哪个功能号、哪张表、哪个字段实际发生了什么；产出供根因判读、代码定位、数据对账共用，每条事实都要带原文、行号与时间戳。

本技能只做解析，不做判读：解析给的是事实（某时某行出现了什么、字段值多少、某事务更新了哪几张表），是不是根因须由判读者结合代码证据下结论，把解析产物直接当根因是本领域最常见的误判。

取材沿证据链走：现象落成时间窗，时间窗圈定节点，节点定到日志文件，文件里用功能号与错误码锁住命中行，最后顺功能号接到 redo 与报文；任一环缺料写待补输入，不猜补。日志四类分治：UFT 运行日志（含死锁 dlog）、报盘日志（直报、新老分仓、前置机）、报文日志（T2 包与客户端 T2 日志）、redo（落库与业务快照两类，工具不通用）。

触发词：日志检索、redo 解析、报盘日志解析、报文解析、死锁分析、耗时与配置件提取。只读代码或库表即可定论、要直接给根因或性能定性、素材无法取回且不需要待补清单的场景不适用。

## 执行步骤

### 第一步：定段别

判据是解析器能否「给附件路径加 JSON 开关、零业务参数跑完」：能的是机器段，素材钉版时自动试跑、产物进素材清单；不能的是手工段，含检索型、参数驱动型（要股东号、委托号）、对照型（要另一侧数据）、交互式与二进制。做法是先消费清单已有产物、缺则补；反例是把检索型脚本塞进自动试跑，零结果后误判现场没日志。

### 第二步：素材预处理

解包、编码探测、表头先核做在解析前。解包优先系统自带命令，不行回退专用库；解到素材目录或临时目录，证据锚指向解压后文件与行号。编码：现场 GBK 与 UTF-8 双态并存，手选错编码不报错、只让中文静默消失，首读前先探测再抽查一个中文标记（如发送报文），已内置自动编码的不手工指定。表头：写临时脚本前先读表头行锁定实际列名，列契约以实文件为准，不按记忆假设列数。

### 第三步：时间窗与节点

判据是现象有无可定位时点（委托、成交、报错、批次开始）：有就以它为锚向两侧扩窗，高频取分钟级、批量取小时级；无则先问清或粗扫定首个时点；窗口写入证据统一到日期加时分、跨天写年份，不设窗直接扫上百 GB 目录既慢又混入历史同类现象。节点按链路排 UFT 服务端、报盘、前置机、柜台与交易所、数据库回库，哪个先断取哪个，断点两侧都取，只取一侧分不清没发出与没回来。目录与命名先核对：按节点分目录、报盘再按委托处理与成交回报分模块，文件名由任务名或进程名、实例编号、日期组成并按天滚动，多实例靠编号区分，redo 段与死锁日志有独立扩展名，客户端 T2 日志在产品日志目录按日期滚动；反例是拿实例 1 的日志解释实例 0 的现象。

### 第四步：检索收窄

判据是有无可直接过滤的锚：有错误码按错误码捞抛错行及上下文，有功能号按功能号圈入口，只有现象时用预设关键词集（落库失败、初始化、主备切换、redo、序列号、回购六类；redo 含大小写与事务号、合并批键名，手拼必漏）。做法先在单文件验证条件有效，再放开到目录批量跑并输出 JSON；大目录先看摘要分布再精查，一次挂太多关键词命中上万行等于没筛。死锁日志先检索后解析：按 DEADLOCK、已更新、正在更新找出簇，再交解析器用功能号、表名、记录 ID 簇级收窄（簇内任一行命中即整簇保留，防拆散配对），锁顺序取不到标阻塞写待补。

### 第五步：四类日志判读

**UFT 运行日志**看时间戳、功能号、错误码与堆栈：命中行只说明某时某行出现了什么，错误码相同不代表同因，要连取同批相邻行与堆栈段；解析零条不等于无调用，先看自检提示（编码、行头命中、报文标记计数）排除格式变体；日志应存在却查不到时先确认目录覆盖时段与实例，再写待补。

**报盘日志**的直报、新分仓、老分仓、前置机四件套，每段解析功能号以接调用链，重点看调用链、委托时间线、报文头异常与 DealPos 水位线。新老分仓委托申报四段链依次为委托主推、委托确认、分仓申报号更新、成交处理；前置机记 Rec（收请求）与 Send（回应答）配对，委托申报、查委托、查成交各有功能号。三个号禁混：委托号是系统分配的委托序号，申报号是报盘发往交易所的序号，确认号由交易所返回，跨段追踪走脚本换算。断点按段位找：有推送但报盘无申报、有申报但前置机无收到、有应答但确认未回推，断点两侧功能号即定位锚。

**报文日志**里 T2 包是二进制结构，包头含包标记、版本、标志、字段数、记录数与报文标志（区分请求、确认回报与响应），包体是字段定义区加值区；客户端 T2 日志按调用块组织（行头、收发报文、异常信息、调用堆栈、耗时行），行头有带尾冒号与两节、三节线程段变体须同时认；字段提取遇嵌套同名字段要全量返回并标来源，不许静默取首条；报文价值在三方对照：源码取值、接口契约、报文实际值。

**redo** 先判类型再选工具：见事务号、合并批、回库线索的属落库 redo，按事务号组织、合并批内多表混排，用官方工具，窗口锚取回库管理功能号的待处理事务号前后若干事务，不能用错误日志的开始提交事务号（批内独立流水，可能远小于全局事务号）；产物按事务号升序，每记录带事务号、表名、操作与字段值，按表统计给出表清单与记录数。见持仓、比例、因子、资产单元的属业务快照 redo，固定三件套文件，按资产单元、证券代码、组合号过滤，还原变化时间线再与系统当前值对照。判别锚：事务号与合并批走落库，资产单元与持仓走快照。

### 第六步：耗时证据与配置件

耗时素材两类，口径不同不跨件换算。功能号统计 CSV 中文表头约二十列（含功能号、执行次数、平均与最大执行时间），按表头名映射不按列位，缺核心列可见地拒绝解析，负值是采集侧哨兵、原值透出，汇总只对非负求和。性能监控导出分全局概况（约二十八列，含成功执行时间与队列积压）与调用链耗时（约六列），单位微秒，文件名段号即类型锚；最大执行时间异常高要配执行次数看才是热点候选，队列积压看时间序列而非单点。这里只产候选与序列，耗时画像与瓶颈定位不在本技能内。配置件（todb 系 XML）结构容忍，不按文档白名单取键、属性原值全量透出，单元素展平、同名多元素收成带父上下文的列表；现场件常为 GB18030 且声明多字节编码，须先字节解码再进 XML；开关在位用枚举清单表达（不落库、不清理、带唯一索引、带裁剪的表），是事实不是结论；线程数与批内表数关系、合并事务数是否顶格、唯一索引冲突归对应规范判据。

### 第七步：统一契约与证据固定

产物包成同一外壳：任务描述（解析器、源路径、触发来源）、状态（成功、部分、失败、待补、不适用）、事件列表（时间、类别、内容、原始引用）、关键发现（对应证据需求）、指标、抽取值（名称、值、来源引用）、待补输入（缺什么、为什么拿不到）。每条事件与发现带文件加行号的引用，redo 类加事务号区间；全量明细不塞指标字段，指标只放摘要与排序前若干项，全量落伴生工件并登记路径。证据固定要原文照抄（含分隔符与字段顺序）、行号、时间戳三件齐全，缺一降为线索。脱敏只脱身份信息：姓名、证件号、手机号、资金账号、股东号可掩码；功能号、错误码、时间、行号、字段名、报文结构与表名一律保留，它们是复核主键；引用指向未脱敏原件路径，脱敏只作用于展示文本。

## 示例

**按功能号检索**：某类委托在特定时段偶发失败，调用方给了功能号没给错误码，先按功能号收窄再叠时间窗：

```bash
python tools/log_search/log_search.py -d <日志目录> --function-id <功能号> --time-start "08-15 09:00" --time-end "08-15 11:30" --format json --max-results 500
```

命中先看时间分布，集中在两段就切窗取上下文，再逐条记文件名、行号、时间戳与整行原文，同批相邻行一并抄下；发现写成某功能号在某时段某类请求返回某错误码。

**按时间窗检索**：日终回库变慢、目录覆盖整天，没有功能号与错误码，只有时段与现象词，用预设集不手拼。把窗收到回库时段，先用落库失败预设看命中总量，再按错误码精查；同时跑 redo 预设，把失败批与 redo 批次按时间戳对齐。反例是把窗开到全天硬筛，命中混入白天正常批次。

**报文与报盘对账**：客户说某笔委托柜台查不到，链路跨系统、报盘、前置机三段须逐段取证。先用委托号追踪拿申报号与确认号，确认是否真发到前置机；再按请求应答配对看请求体与应答体；若要某股东在某功能号下的全部请求应答与原始报文，按账户过滤落地：

```bash
python tools/ut/parse_front_reqresp.py --dir <前置机COM日志目录> --func <功能号> --stock <股东号> --csv
```

对账并排三样：报盘日志的委托时间线与申报号、前置机请求体的账户与业务字段、应答体的返回码与确认号；三方一致而柜台仍查不到，问题在柜台侧，报文里字段缺失或值被改写则在发送侧。

**redo 关联**：某批数据回库后库里查不到，怀疑批次没落全，线索里有事务号与合并批，走落库 redo。四步：按回库管理功能号的待处理事务号定窗，取窗口前后若干事务的产物（现场解析回传 CSV，或本地同版本工具解析，推荐按表分割并出按表统计）；区间内聚合全部记录不分表即失败批全集；按表分组得批内表清单与各表记录数，与按表统计交叉核对；逐表按各自主键或唯一键取键值，键名以表头或建表定义实读为准，不预设全批同键，再逐条对库查在位性。单事务操作数分布、批内表构成与大事务排序是事实，是否构成积压属判读。

## 完成验证

- [ ] 段别与执行者一致，已有产物先消费未重跑。
- [ ] 编码已探测并抽查中文标记，表头按实文件核对。
- [ ] 时间窗有起止与年份，节点与实例编号对上日志文件。
- [ ] 检索条件先小范围验证，命中行带文件名与行号。
- [ ] 四类日志各按其要点处理，两类 redo 未混用工具。
- [ ] 三个号未混用，跨段走换算，断点两侧证据都取。
- [ ] 事件、发现、抽取值都有原始引用，redo 类带事务区间。
- [ ] 状态如实，缺料进待补输入，未编造解析结果。
- [ ] 展示文本已脱敏，主键字段与结构保留。
- [ ] 解析事实未写成根因，未越界做性能或配置归因。

## 常见踩坑

- **手选编码硬读日志**：判据是编码未探测；做法是先探测再抽查中文标记；反例是 GBK 按 UTF-8 读后中文静默消失，还写成日志无该关键字。
- **解析零条就写无调用**：判据是未看自检提示；做法是先查编码、行头命中与报文标记计数；反例是行头变体导致全漏，结论写成客户端未发起。
- **按记忆假设表头**：判据是列名列位未对实文件；做法是先读表头两行再映射；反例是照文档写死列数，实际列数不同而连跑两次全空。
- **两类 redo 混用工具**：判据是素材里出现事务号还是资产单元；做法是按判别锚分流；反例是把回库 redo 段喂给快照解析器，两边都空。
- **窗口参数取错号**：判据是取了批内流水而非全局事务号；做法是取回库管理功能号的待处理事务号前后；反例是拿开始提交事务号当窗口，批次错位。
- **三个号混用**：判据是把委托号当申报号检索；做法是按语义各取各号、跨段走换算；反例是零命中后误判报文没发出。
- **报文同名字段取首条**：判据是嵌套数据集里有同名字段；做法是全量返回并标来源；反例是只取第一层，金额方向判反。
- **把解析产物当根因**：判据是结论无代码或契约证据支撑；做法是事实与判读分开交付；反例是把日志有超时写成某组件性能不足。
- **证据缺行号或未脱敏**：判据是引用只有文件名或展示文本带完整账号；做法是补行号、身份掩码、主键保留；反例是原文整段贴出，既无法定位又泄露客户信息。
- **手拼预设关键词**：判据是 redo 这类多写法词靠人手凑；做法是直接用预设集；反例是只搜小写写法，漏掉变体与事务号键名。
- **拿不到材料就编结果**：判据是反复解析仍无产物；做法是写待补输入注明缺什么；反例是补一段看似合理的日志片段流出，后续全链返工。
