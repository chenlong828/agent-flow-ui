## 适用场景

你拿到了开发交付的修改事实：改了哪些行为、有哪些场景种子、哪些断言锚点已经查证、回归范围是什么。你要回答三个问题：要测什么、测多深、什么算通过。产出是一份测试设计（用例矩阵 + 数据需求 + 断言引用 + 缺口清单），供造数、用例生成、执行三个阶段直接消费。

本技能不写代码、不造数、不生成可执行脚本、不下定性结论、不流转状态。设计决策只依据上游事实，不重新读源码做推断；缺依据时列缺口并派补齐，不臆测。

触发词：测试设计、用例矩阵、测试点、断言锚、覆盖、缺口、回归范围、数据需求。

不适用：已经有可执行用例、只需要执行；探索性测试；没有上游修改事实的盲测。

## 执行步骤

### 第一步：收基线，核对交接

测试设计只能建立在四类事实之上：

| 基线 | 内容 | 缺失时 |
|---|---|---|
| 行为 delta | before（旧行为）、after（新行为）、unchanged（未变但受影响） | 退回开发补齐，不设计 |
| 场景种子 | 每个 delta 对应的正向、反向、边界场景 | 列 scenario_gap |
| 断言锚点 | 错误码、日志点、字段、行号，且已查证 | 列 anchor_gap |
| 回归范围 | 受影响入口清单与抽样方式 | 退回补齐 |

四项缺任一项，先补再设计，不带病规划。基线核对完成后固定下来，后续只读这一份，不反复回上游翻文件。

### 第二步：做三组映射

**映射一：变更 → 测试项。** 每条 delta 至少一个用例：

- after（新行为）→ 正向用例 + 反向用例（锚点驱动）+ 边界用例（断言只写「行为确认」，不写死预期）。
- before（被替换的旧行为）→ 不单独设用例；如果旧路径入口在回归范围内，设回归确认用例。
- unchanged（未变但受影响）→ 每条至少一个防误伤用例。

**映射二：场景 → 用例。** 场景类型决定用例类型：

- 新增拒绝类（new_reject）→ 正向 + 反向 + 边界 + 位置/组合变体。
- 回归确认类（regression_confirm）→ 回归确认用例，引用原场景输入。
- 邻域防护类（neighbor_guard）→ 防误伤用例。

种子已经构成完整正反边界覆盖的，直接引用；覆盖不全的，补用例或列 scenario_gap，不凭感觉补。

**映射三：锚点 → 断言。** 断言必须引用已查证的锚点或补齐后的代码事实，锚点类型决定断言形态：

| 锚点类型 | 断言形态 |
|---|---|
| 错误码 | 匹配错误码与错误信息 |
| 日志点 | 匹配关键字与级别 |
| 字段/行号 | 比对字段值与位置 |
| 页面元素 | 断言元素存在与文案 |

没有锚点就不写断言，列 anchor_gap。自然语言描述的「应该报错」「结果正确」不能当断言。

一个用例等于一次调用、一个断言判定。同一用例覆盖的多个分支如果断言码不同或入口不同，拆成独立用例，或声明「主分支实例化、其余列为扩展项」；不拆会在生成阶段被裁剪，回退重做。

### 第三步：生成用例矩阵

每条用例至少包含：

| 字段 | 说明 |
|---|---|
| tc_id | 用例编号 |
| category | 正常 / 边界 / 异常 / 数据一致性 / 性能 / 回归 / 防误伤 |
| scenario_ref | 对应场景种子 |
| entry | 功能号与服务名 |
| objective | 一句话测试目标 |
| data_requirement | 数据种类、规模、唯一性、前置条件 |
| execution_entry | 执行入口（可与写入入口不同） |
| assertion_refs | 锚点 ID、类型、来源 |
| priority | P0 / P1 / P2 |

矩阵之外单独汇总数据需求，供造数阶段直接使用；缺数据需求的用例视为不完整。

覆盖基准：回归范围内每个受影响入口至少正向 1 条 + 异常 1 条；有邻域防护场景的入口再加防误伤 1 条；共享组件或多通道按抽样建议执行。性能用例只在影响面涉及性能路径时设立，且必须有基线来源，没有基线就降档，不写「含基线对比」。

### 第四步：列缺口并补齐

缺口分三类，每类都要写清「缺什么、为什么现有素材补不了、建议从哪里补」：

- scenario_gap：场景覆盖不足，缺正向、反向或边界变体。
- anchor_gap：断言锚点不足，错误码、日志点、字段位置未查证。
- data_premise_gap：数据前提不明，存量约束、隐藏前置、号段冲突未确认。

缺口非空时派补齐；补齐后回填并复跑，缺口清零才可放行。人审确认豁免的缺口要记录豁免人与理由。

### 第五步：准出

设计准出看四件事：每条 delta 都有用例；每条用例都有断言引用与数据需求；缺口清零或有豁免；覆盖基准逐项满足。四项都满足才交给生成阶段。

### 用例矩阵片段

```json
{
  "tc_id": "TC-T01",
  "category": "正常",
  "scenario_ref": "S-01",
  "entry": {"func_id": 1000123, "service": "entrust_query"},
  "objective": "按委托号查询返回该笔委托",
  "data_requirement": {"kind": "存量委托", "scale": "1 笔", "premise": "委托状态为已报"},
  "execution_entry": {"func_id": 1000123, "note": "写入链与验证链同一入口"},
  "assertion_refs": [{"anchor_id": "RI-007", "type": "field_match", "source": "code_facts"}],
  "priority": "P0"
}
```

字段缺一项就退回补全，不接受「先跑起来再补」。

### 覆盖核对表

| 检查 | 判据 | 不通过的处理 |
|---|---|---|
| delta 覆盖 | 每条 after 至少一条用例 | 补用例或列 scenario_gap |
| unchanged 覆盖 | 每条至少一条防误伤 | 补用例 |
| 入口覆盖 | 回归范围每个入口正向 + 异常 | 补入口用例 |
| 断言覆盖 | 每条用例至少一个已查证锚点 | 列 anchor_gap |
| 数据覆盖 | 每条用例有数据需求 | 补数据需求 |
| 分支拆分 | 一个用例一次调用一个判定 | 拆用例 |

核对表逐项打勾后才能交给生成阶段。

## 示例

**示例一：接口新增拒绝分支**

delta：after 为「资金不足时返回错误码 E1001」。场景种子：正常委托、资金不足、资金刚好等于委托金额。锚点：错误码 E1001 已查证，字段 available_amt 已查证。

设计三条用例：正常委托（正向，断言返回成功与字段值）、资金不足（反向，断言 E1001）、边界相等（边界，断言行为确认 + 字段比对）。三条数据需求分别写「足够资金」「不足资金」「刚好相等」，造数阶段按此准备。

**示例二：共享组件修改**

delta：公共查询组件改了空值处理。回归范围列了 6 个入口，抽样 3 个。设计：每个入口正向 1 条、空值 1 条；抽样入口之外补 1 条邻域防护。缺口：其中一个入口的断言锚点未查证，列 anchor_gap，补齐后再放行。

**示例三：缺口驱动补齐**

设计到一半发现「超时」场景没有可断言的日志点，列 anchor_gap，写明「需要定位超时分支的日志输出位置」。补齐返回日志点与行号后，补一条断言引用，缺口关闭。

## 脚本

无脚本。输出为测试设计 JSON：任务引用、覆盖基线与抽样、用例矩阵、数据需求汇总、缺口清单、阶段交接说明。字段名可按调用方约定调整，但矩阵的九项字段不能少。

## 完成验证

- [ ] 四类基线齐备，缺失项已退回补齐。
- [ ] 每条 delta 至少一条用例；unchanged 有防误伤用例。
- [ ] 每条用例都有断言引用，且锚点已查证。
- [ ] 每条用例都有数据需求，并汇总到数据需求清单。
- [ ] 一个用例只做一次调用、一个断言判定；多分支已拆。
- [ ] 缺口三类分型清楚，清零或有豁免记录。
- [ ] 覆盖基准逐项核对通过。

## 常见踩坑

- **脱离事实自创场景**：上游没给的场景自己编，设计与实际改动脱节。场景只能来自种子或缺口补齐。
- **断言引用未查证锚点**：用例看着完整，执行时无法机判。锚点必须标来源与查证状态。
- **缺口不列硬放行**：设计带洞进入生成，后面返工成本更高。缺口清零是准出门槛。
- **用例缺数据需求**：造数阶段没有依据，执行阶段无法绑定。每条用例都要写。
- **一个用例塞多个分支**：断言码不同还合并，生成阶段只能裁剪。拆开或声明扩展项。
- **边界用例写死预期**：边界行为未定时写「必须报错」，会把正常行为误判成缺陷。只写行为确认。
- **性能指标拍脑袋**：没有基线还写「含基线对比」，结论不可信。按档位降级并注明来源。
