## 适用场景

你手上有一份现场缺陷的分析材料：一条 5Why 追问链、根因归类与改进措施。输入可能是聊天里的文本、一个 Markdown 文件，或从效能平台按编号拉回的分析字段（常带 HTML 标签，需先清洗）。任务是评审：逐层核对因果与证据，判断根因是否成立、深度够不够，判断措施能否落地并防止再发，最后给出可签字的分级结论与能回贴平台的修正稿。

产物是评审意见四段：逐层逻辑判断、带置信锚与备选根因的根因结论、措施逐条评审与覆盖分析、结论分级加修正稿。每条判断都要能回指原文的哪一句。

本技能只评审，不改排查。定位结论、修复方案、责任划分、排期都不在范围内：现象未定性的先退回排查，只做代码定位的走代码检查。链条缺证据要提交人补，绝不替他补一层看似合理的因果，否则会把未经证实的推断写进经验库。

触发词：5Why 评审、根因分析评审、缺陷分析评审、改进措施评审、复盘评审。

不适用：现象未定性；只需代码定位；只需缺陷数据统计。

## 执行步骤

### 第一步：拆成四块并对齐结构

判据：材料至少能拆出现象与影响、时间线、5Why 链、改进措施四块。缺 5Why 或缺措施按未完成处理，不推测补全。

做法：按标题关键字定位，没有标题按段落语义切，切完标出来源位置。时间线常不单独成节，要从现象与日志摘录里抽，抽不到即记缺口。

反例：把问题描述和 5Why 混着读，把现象复述当成第一层 Why 的证据，整条链看着有证据，实际在重复同一句话。

### 第二步：事实与推断分离

判据：能被另一个人在同样的系统里独立复核的才是事实；要依赖说话人的判断、记忆或解释才成立的，是推断。两者必须分开写。

做法：逐句打标记。事实落到四类锚点之一：带时间戳的系统记录、可复现的查询结果、版本与提交信息、缺陷单原始描述。推断写成「依据某事实，判断某某」。

反例：把「开发自测没覆盖该分支」当事实，实际没有任何自测记录，只是从线上出问题倒推。应先写事实「该分支无自测用例记录」，再写推断「据此判断自测未覆盖」。

### 第三步：重建时间线

判据：时间线要对齐引入、触发、暴露三个时刻。对不齐说明还没搞清缺陷怎么进来的，此时谈根因没有意义。

做法：系统记录按时间排序，标出关键动作的发起方与结果。引入看版本比对与变更记录，触发看首次异常的请求或任务，暴露看告警、客诉、对账差异。

反例：只写「某日上线后出现异常」，把引入与暴露当同一时刻，根因就被引向最近一次改动，而缺陷在更早的提交里。

### 第四步：区分直接原因与根本原因

判据：直接原因指认本次故障由哪个动作或状态直接引发，通常是一个错误值、错误分支或缺失步骤；根本原因回答为什么它能发生、能过评审与测试、能跑到线上，落在流程、设计约束、检测能力或制度上。

做法：先找直接原因，它要能解释现象主体并被日志或数据印证；再沿「为什么没被拦住」往上追到可改动的一层。

反例：把「代码少了一个判空」当根本原因。它解释得了本次报错，但让缺漏通过评审与测试的条件一条没变。

### 第五步：逐层追问 5Why

判据：第 N+1 层必须真正回答第 N 层的为什么，并带来新信息。同义改写、绕回已说过的内容，判逻辑断裂。

做法：每层问四句：是否回答上一层的为什么，连读两层读不通即跳步；依据是事实还是推断；有没有引入新环节；指向的对象能否被改动。深度分档：满五层且递进判通过；三到四层但连续判部分通过并指出缺口；不足三层或中间断裂判不通过。

四种坏链要点名：过早收束，给个「测试不充分」就停住；循环归因，两三层之间互相解释；归因于人，终点是疏忽、经验不足；伪根因，写「设计不够详细」这类无法量化的表述。

反例：「为什么没发现，因为测试不充分；为什么测试不充分，因为用例不全；为什么用例不全，因为需求变更」。读着有四层，实为同义递推，没回答用例为什么没跟着变更更新。

### 第六步：判定何时停止追问

判据：同时满足三条才停：这一层可改动，有人有权改它；再追问一层没有新信息；改动这一层能真正阻断复发。

做法：可停的落点有四类：流程规则缺失、工具能力缺失、设计约束缺失、知识缺口。超出本项目权限时，不硬改，写缓解措施并注明受限于哪条制度。

反例：最后写「根因是开发人员疏忽」。它不可改动也不可验证；追问「为什么流程没防止这次疏忽」，本可得到「合并前没有该分支的必检项」这个落点。

### 第七步：人为因素与系统因素

判据：人为因素回答谁做了什么动作，系统因素回答什么条件让这个动作可能发生且没被拦住。系统因素写在根因位置，人为因素写成触发条件。

做法：遇到「人做错了什么」，反问三句：他当时掌握的信息是否足以做对；哪个检查点本应拦住它、为什么没起作用；换个熟练的人来做是否同样容易犯。第三问答同样容易，就不是人的问题。

反例：「加强责任心，提交前多检查一遍」。没有责任人可落实、没有验收口径，也没改变让错误通过的条件。

### 第八步：评审防再发措施

判据：及格措施同时满足三件事：对应一个已确认的根因；可执行，有责任角色、时间节点、验收口径；能防再发，改变缺陷通过的条件，而非只让它更容易被发现。

做法：先按类型分类，再逐条核 SMART。

| 类型 | 判据 | 例子 |
|---|---|---|
| 技术措施 | 改代码、配置或工具，使同类错误不可能发生 | 取数加幂等键；换算收敛到公共方法 |
| 流程措施 | 某一环节增加必过动作，且有产出物 | 变更单附影响面声明；跨模块改动需第二人签字 |
| 检测措施 | 提高发现能力，不改变错误发生的可能 | 补该分支用例；差异金额加对账告警 |

检测不能替代技术与流程。全部措施都是「增加检查」，说明根因没被真正处理，结论最多合格并要求补治本项。每条措施写清责任角色、期限与可被第三方判断的验收方式，「相关同学已知悉」这类表述不可验收。每个根因至少一条措施；没有根因对应的措施，要么删，要么补写它对应的被漏掉的根因。

反例：根因「测试未覆盖边界值」，措施「加强用例设计」。没说哪个模块哪个边界、谁在何时补、补完怎么验证，也没改变用例评审的触发条件。

### 第九步：复盘评审与结论分级

判据：评审是三段闭环：初审判定、确报签字、落地登记。三段都有记录才算完成；只出意见不登记落地，等于没评审。

做法：初审逐层过链与措施，形成带证据锚的候选问题清单，没有原文引用位置的候选无效。确报给每条候选定性，确认记下确认人，驳回记下理由。落地登记责任角色、期限与验证方式，下次出现同类缺陷时回看措施是否真生效。归档后不再改写，修正以追加记录进行。

结论分五档：

| 等级 | 判据 | 处置 |
|---|---|---|
| 优秀 | 链条完整递进，根因在系统层，措施含治本项且可验收 | 通过，可沉淀经验 |
| 良好 | 链条基本完整，个别层证据偏弱，措施可执行 | 通过，附可选优化 |
| 合格 | 层数不足或个别跳步，措施存在但不完善 | 有条件通过，限期补齐 |
| 不合格 | 断裂、循环归因或止于人为，措施空泛 | 退回重写 |
| 未完成 | 缺 5Why 或缺措施 | 退回补全，不计分 |

计分：通过计一、部分通过计半分、不通过计零分，5Why 与措施各占一半权重。根因结论必须带离散置信锚：可直接证实记 100，强证据仍需判断记 75，依赖未验证假设记 50，只有模式直觉记 25，纯猜测记 0。低于 75 必须同时列备选根因与验证方式；两个独立来源指向同一根因可晋级一档。

反例：写「根因置信度 0.83，建议通过」。连续分数无法对应行为判据，读者判断不了数从哪来。

### 第十步：写报告与回贴稿

判据：报告要让没参与排查的人能独立复核，每条判断后要有原文摘引；回贴稿要能直接粘回平台，必须是纯文本。

做法：报告顺序固定：基本信息、评审概要、逐层逻辑评审、根因结论、措施评审、覆盖分析、按优先级排序的优化建议、总结、修正稿。回贴稿每层两行，W 序号加问题、A 序号加答案，措施每条一行并写责任角色与时间节点。原文无需修改时写明「原始分析无需修正，建议维持原提交」。

反例：只写「整体质量一般，建议补充」，没说哪层缺证据、缺什么证据，提交人无法据此修改。

## 示例

### 示例一：一条完整的 5Why 链

材料：批量任务在数据量放大后重复扣减，账户余额比预期少一笔。

W1 为什么余额少一笔？A1 同一笔业务被扣减两次，依据是同一业务号有两条扣减记录。W2 为什么扣减两次？A2 超时重试时重复处理了同一批数据，依据是同一批次被两次拉取。W3 为什么重试会重复处理？A3 取数只判「待处理」状态，处理中不改状态。W4 为什么只判状态？A4 设计时默认单实例运行，没有考虑重试与并发，依据是设计文档该章节没有重入描述。W5 为什么设计阶段没约定重入语义？A5 同类任务没有统一的设计必检项，依据是六个同类任务里四个同样没有幂等保护。

评审判定：五层递进，根因落在设计必检项缺失这一系统层，锚点齐备，判优秀。对应措施为写入加幂等键、把重入与幂等写进设计检查清单。

### 示例二：止步于人为因素的错误示范

材料原文：W1 为什么余额不对？A1 因为重复扣了款。W2 为什么重复扣？A2 因为开发漏改了一个分支。W3 为什么漏改？A3 因为开发人员疏忽。W4 为什么没仔细检查？A4 因为时间紧、责任心不足。

评审结论：判不合格并退回。W3 与 W4 都停在人的态度上，既不可改动也不可验证；链条没有回答「为什么漏改的分支能通过评审与测试」，而这正是唯一能改进的地方；「时间紧」是推断而非事实，没有排期记录支撑。

改写方向：W3 换成「该分支没有任何用例或静态检查覆盖，合并前的检查清单也不含它的必检项」，并补合并请求的检查项记录作事实锚；W4 换成「检查清单由个人经验维护，没有按模块定义必检项」，落点从态度转为流程规则。

### 示例三：防再发措施的三种类型

场景：查询接口在字段为空时返回上一笔缓存结果，页面显示错位；根因是缓存写入没有按请求参数区分维度，接口层也没有对空结果做处理。

技术措施：缓存键改由全部查询参数拼接生成，收敛到一个公共方法，禁止调用点自行拼接；责任角色为模块负责人，期限下个迭代，验收口径为该方法的单测覆盖参数顺序与空值两种情形。

流程措施：接口设计模板增加「缓存键构成」一栏，未填写不予评审通过；责任角色为设计评审组织者，期限两周内生效，验收口径为下一份设计文档的评审记录中出现该栏。

检测措施：同一接口连续两次不同参数的请求增加返回内容比对，结果相同且参数不同时告警；责任角色为值班负责人，期限一个月内上线，验收口径为测试环境能构造该场景并触发告警。

评审结论：三条覆盖治本、防漏与发现三个方向，判优秀；若三条都写成「增加检查」，最多判合格。

## 脚本

无脚本，纯文本评审，不依赖外部工具。评审结论按以下契约组织，字段缺失时留空并写明缺口：

```json
{
  "completeness": {"phenomenon": true, "timeline": false, "why_chain": true, "measures": true},
  "why_review": [
    {"level": 1, "question": "", "answer": "", "verdict": "pass|partial|fail",
     "anchor": "", "comment": ""}
  ],
  "root_cause": {"direct": "", "root": "", "layer": "process|tool|design|knowledge",
                 "confidence_anchor": 0, "alternatives": [{"cause": "", "verify_by": ""}]},
  "measures": [
    {"id": 1, "content": "", "root_cause_ref": "", "type": "tech|process|detect|spec|training",
     "owner_role": "", "due": "", "acceptance": "", "verdict": "pass|partial|fail"}
  ],
  "conclusion": {"grade": "A|B|C|D|F", "decision": "pass|conditional|return", "must_fix": []}
}
```

`verdict` 只能取三个值；`confidence_anchor` 只能取 0、25、50、75、100 五个整数；`must_fix` 按严重程度排序，最多五条，每条都要能对应到某一层的改写或某条措施的补齐。报告与回贴稿都由这份结构渲染，两者不得矛盾。

## 完成验证

- [ ] 四块材料已拆出，缺口已记录，没有替提交人补内容。
- [ ] 每条判断都有原文摘引或证据锚点，事实与推断已分开。
- [ ] 时间线对齐了引入、触发、暴露三个时刻，或写明原因。
- [ ] 直接原因与根本原因都写了，且不是同一句话的改写。
- [ ] 逐层核对过是否回答上一层的为什么，跳步与循环归因已点名。
- [ ] 没有在人为因素上收尾，根因落在可改动的一层。
- [ ] 根因结论带离散置信锚，低于 75 时列了备选根因与验证方式。
- [ ] 每条措施都有责任角色、期限、验收口径，至少一条为治本项。
- [ ] 结论分级有判据支撑，退回意见按可执行顺序排列。

## 常见踩坑

- **把推断写成事实**：直接下结论「测试没覆盖」，不写依据是哪份记录。应把事实与推断分两行写，推断句以「据此判断」开头。
- **替提交人补链**：觉得提交人写得不好，顺手替他想了一层根因，补出来的层没有证据，等于把评审意见变成新的未经验证的材料。
- **在人为因素上收尾**：写「疏忽」「责任心不足」「时间紧」当根因，既不可改动也不可验证。
- **把直接原因当根因**：写「少了一个判空」就收工，让缺漏通过评审与测试的条件一条没变。
- **措施没有验收口径**：写「加强评审」「提升意识」，没有责任角色、期限和可判断的完成标准。
- **根因与措施对不齐**：某个根因没有任何措施说明改进漏项，某条措施没有根因说明措施是凑数的。
- **用连续分数表达置信**：写「置信度 0.83」，必须换成离散五档锚并写清支撑它的行为判据。
- **把复盘当成重开排查**：评审时顺手改排查结论与责任划分，复盘只评审材料质量与改进落地。
