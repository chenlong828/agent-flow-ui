## 适用场景

你只知道一个业务说法——「债券偏离度」「委托撤单」「资金可用」——不知道它在代码里的位置。你要沿「产品 → 业务域 → 价值流 → 场景 → 功能号/菜单 → 代码入口」逐级定位，产出一条可核对的路径链，而不是一上来就全仓检索。

本技能负责业务到入口的映射，不负责读源码细节。定位到入口后，具体实现由代码现状检查接手；入口对应的服务名、V 卡由知识图谱技能接手。

触发词：业务功能树、业务域、价值流、功能号、菜单定位、这个功能在哪、入口在哪。

不适用：已经知道精确文件路径或功能号；需要评估改动影响面；需要读代码确认实现。

## 执行步骤

### 第一步：定产品

同一个业务词在不同产品里指向不同模块，先定产品再定树。

- 需求单里没有产品信息时，用「有权限的产品列表 + 需求编号反查」确定产品；不要凭需求标题猜。
- 用户直接说了产品，以用户为准，但仍要记录来源。
- 产品确定后，读取该产品的知识入口：产品概述、菜单结构、变更传导规则。产品到知识文件的映射查产品映射表，不写死在技能里。

产品不确定时，整条路径都不可信，先停下来问清楚。

### 第二步：定业务域与价值流

把业务词映射到业务地图上的两级：

- 业务域：交易、账户、资金、查询、清算交收、资讯、风控、报盘等。
- 价值流：业务从哪一步到哪一步，例如「委托处理」包含下单、撤单、改单、回报；「估值」包含行情、偏离度、重算。

判定方法：先看业务词里的核心名词落在哪个域，再看动词落在价值流的哪一段。例如「债券偏离度」核心名词是偏离度，属于估值域；价值流是估值监控。

业务域或价值流对不上时，不要硬塞进最像的一级。列出 2–3 个候选，写明各自的判断依据，交给用户确认。

### 第三步：定场景与功能号

在选定的业务域与价值流下，找具体场景，再取功能号或菜单：

| 层级 | 来源 | 产物 |
|---|---|---|
| 场景 | 业务地图/场景清单 | 场景名与一句话描述 |
| 菜单 | 菜单结构文件（按产品） | 菜单名、菜单 ID、路由 |
| 功能号 | 菜单表、功能号字典、源码注册点 | 功能号、所属模块 |

定位顺序：先查菜单结构里的名称与路由，再查功能号字典；菜单里没有显式功能号时，去源码的功能号注册文件反查。功能号在字典与源码里不一致时，以当前版本源码为准，并记录差异。

### 第四步：落代码入口

页面入口：路由 → 页面组件目录。路由末段通常对应 views 下的目录名，目录内有页面结构文件与配置模板。

后端入口：功能号 → Controller → Service。按功能号段归属到对应服务，再按 `功能号 + Controller`、`功能号 + Service` 的文件名规则找。

入口只记路径与文件，不读实现。需要确认「这个功能到底做了什么」时，转代码现状检查。

### 第五步：出路径链与候选

最终产物是一条链，每级都带证据：

```text
产品：机构算法总线 1.0（来源：需求反查）
业务域：估值（来源：业务地图 §x）
价值流：估值监控（来源：业务地图 §x）
场景：债券偏离度（来源：场景清单）
功能号：f10xxx（来源：菜单表）
页面入口：views/valuation/deviation/index.vue（来源：路由表）
后端入口：F10xxxController / F10xxxServiceImpl（来源：功能号字典）
```

证据等级：菜单表/字典 = 高；业务地图 = 中；命名相似 = 低。低等级证据不能单独作为入口结论，只能列为候选。

候选不唯一时全部列出并排序：业务域匹配优先，其次入口完整度，最后更新时间。排序只用于建议，不替用户做最终选择。

### 知识入口对照

每个产品至少备三类知识入口，缺一类就有一级定位做不了：

| 入口 | 内容 | 用来回答 |
|---|---|---|
| 产品概述 | 产品定位、模块划分、术语 | 业务词属于哪个产品与域 |
| 菜单结构 | 菜单名、菜单编号、路由 | 入口在哪、页面叫什么 |
| 功能号字典 | 功能号、服务名、所属模块 | 后端落点、服务归属 |
| 环境映射 | 开发、测试、生产的地址 | 页面验证与接口核对 |

入口文件随产品不同而不同，查产品映射表获取路径，不在技能里写死。入口缺失时登记为知识缺口，不拿旧版本文档凑。

### 候选评分

同一业务词命中多个入口时，按三项打分：

| 维度 | 权重 | 判据 |
|---|---:|---|
| 业务域匹配 | 高 | 候选所在域与需求描述一致 |
| 入口完整度 | 中 | 页面、路由、功能号三级是否齐全 |
| 时效 | 低 | 最近更新时间与当前版本是否一致 |

评分只用于排序建议，不替代用户确认。两个候选同分时并列输出，说明差异点，让用户选。

### 路径链模板

```text
产品：
业务域：
价值流：
场景：
菜单/功能号：
页面入口：
后端入口：
证据等级：
未确认项：
```

每一级都写来源（文件、节、行号或知识条目），没有来源的级别标「待确认」，不省略。

## 示例

**示例一：债券偏离度**

用户说「查一下债券偏离度在哪」。产品=机构算法总线；业务域=估值（偏离度属于估值监控）；价值流=估值监控；场景=债券偏离度；菜单=估值 → 偏离度监控；功能号=f10xxx；页面入口=views/valuation/deviation；后端=对应 Controller 与 Service。每级都记录来源；没有读任何实现代码。

**示例二：委托撤单**

用户说「撤单功能」。这个词跨域：交易域有撤单，查询域也有撤单记录查询。先列两个候选：交易/委托处理/撤单（可操作），查询/委托查询/撤单记录（只读）。追问用户要「能撤单的操作」还是「查撤单记录」，确认后再往下取功能号。

**示例三：菜单名与功能号不一致**

菜单结构里写「资金查询」，功能号字典里同一入口登记为「可用查询」，源码注册点又是另一个名字。三个名字指向同一路由时，以路由为锚，把三个名字都记下来；路由不同则是三个功能，不能合并。

## 脚本

无脚本。可用等价的检索命令辅助（按菜单名查路由、按功能号查字典、按路由查目录），但结论必须回到「菜单/字典/路由」三类证据，不用文件名相似度充当证据。

## 完成验证

- [ ] 产品已确定，来源可回指。
- [ ] 业务域与价值流有业务地图依据，不是凭字面猜。
- [ ] 场景、菜单、功能号三级齐全，缺级写明原因。
- [ ] 页面入口与后端入口都有路径或文件名。
- [ ] 每级证据等级已标注；低等级证据只作候选。
- [ ] 候选不唯一时列全并说明排序依据。

## 常见踩坑

- **跳过产品直接找代码**：同一业务词在不同产品下是不同模块，先定产品能省掉大半无效检索。
- **用菜单名当功能号**：菜单名会改，功能号稳定；两者对不上时以路由和字典为准。
- **业务域硬塞**：找不到对应域就塞进最像的一级，后面整条链都错。列候选比硬判好。
- **跳级检索**：跳过价值流直接全文搜业务词，命中太多且无法收敛。
- **把命名相似当证据**：文件名像不代表是同一个功能，必须有菜单、字典或路由证据。
- **入口当实现**：定位到文件就以为完成了，实际还要读代码确认行为；入口只是下一步的起点。
