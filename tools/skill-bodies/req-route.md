## 适用场景

你收到一条原始诉求：需求单、缺陷单，或一句话描述。你要在动手之前回答四个问题：这是什么类型的改动、属于哪类动作、要动多大、应该交给谁。产出是一张路由卡，供下游专家接手。

本技能只做意图分析与分流，不写需求文档、不设计方案、不估具体工期。分析结论必须建立在已取证的事实上：改动文件数、涉及层级、是否已实现，都要有代码或知识库证据；拿不到证据的，标为待确认，不用「大概率」「可能」代替。

触发词：需求分类、动作判定、加按钮、加逻辑、加现有、加模块、加菜单、修缺陷、多标签、大小需求、路由。

不适用：需求已经拆到任务级、只需要执行；只需要查代码现状；只需要评估某个改动的影响面。

## 执行步骤

### 第一步：判功能类型

先判三选一，它决定后续走哪条路：

- 新增功能：系统里原本没有这个能力。
- 修改现有功能：能力存在，要改行为、展示或口径。此类必须先做已实现检测。
- 缺陷修复：预期与现状不符，有可复现现象。缺陷类不走「新增」分支。

不属于功能开发的（定位、排查、异常调查）单独归为「问题排查」，路由到排查流程，不进入需求交付链。

### 第二步：定主动作与二级动作

动作分类回答「这个需求到底在做什么」，与影响范围、难度、规模是四个正交维度。一级七类，二级按下表判定：

| 一级 | 二级 | 判据 | 典型分层 | 识别信号 |
|---|---|---|---|---|
| 加按钮 | 气泡提示 | 悬停或点击出现说明，不调后端 | 前端 | 提示、tooltip、问号图标 |
| 加按钮 | 弹窗提示 | 弹出对话框展示或确认，不调后端 | 前端 | 弹窗、确认框、dialog |
| 加按钮 | 接口调用 | 点击触发后端接口，执行业务动作 | 前端 + 后端 | 按钮、执行、触发、导出 |
| 加按钮 | 前端交互 | 纯前端行为，展开收起、高亮、拖拽 | 前端 | 展开、高亮、拖拽、复制 |
| 加逻辑 | 计算逻辑 | 新增字段计算、统计、汇总、金额 | 后端，可能到核心 | 计算、统计、汇总、公式 |
| 加逻辑 | 校验逻辑 | 输入校验、权限校验、业务规则校验 | 前端 + 后端 | 校验、必填、格式、限制 |
| 加逻辑 | 过滤逻辑 | 查询条件新增或修改，筛选范围变化 | 前端 + 后端 | 筛选、过滤、查询条件 |
| 加逻辑 | 排序逻辑 | 排序规则新增或修改 | 前端 + 后端 | 排序、排列、order |
| 加逻辑 | 转换逻辑 | 格式转换、编码映射 | 后端 | 转换、映射、编码转中文 |
| 加逻辑 | 开关逻辑 | 配置项控制行为分支 | 前端 + 后端，可能到配置层 | 开关、启用、禁用、配置 |
| 加菜单 | 新页面 | 新增完整页面，含路由、组件、可能含接口 | 前端，可能加后端 | 新页面、新菜单、新 tab |
| 加菜单 | 新路由 | 只加跳转，不建页面 | 前端 | 路由、跳转、redirect |
| 加菜单 | 新权限 | 新增权限项，控制可见性或操作 | 前端 + 后端 | 权限、角色、菜单权限 |
| 加模块 | 查询模块 | 新增查询列表页，含条件、表格、可能导出 | 前端 + 后端 | 新增查询、列表页 |
| 加模块 | CRUD 模块 | 新增完整增删改查 | 前端 + 后端 + 数据层 | 增删改查、新建编辑删除 |
| 加模块 | 配置模块 | 新增参数维护、字典管理 | 前端 + 后端 + 数据层 | 配置管理、参数维护 |
| 改现有 | 改展示 | 改列、布局、样式，不动逻辑 | 前端 | 修改列、调整布局、改样式 |
| 改现有 | 改交互 | 改操作流程或交互行为 | 前端 | 改交互、调整行为 |
| 改现有 | 改性能 | 查询慢、渲染卡顿的优化 | 后端，可能到索引或核心 | 优化、性能、超时、慢 |
| 改现有 | 改数据口径 | 统计口径、计算规则变更 | 后端，可能到核心 | 口径变更、统计规则 |
| 修缺陷 | 空指针 | 空值导致的异常 | 前端或后端 | 空指针、null、报错 |
| 修缺陷 | 逻辑错误 | 条件判断或分支写错 | 前端或后端 | 逻辑错误、判断错 |
| 修缺陷 | 数据错误 | 数值、字段、口径算错 | 后端 | 数据不对、数值错、字段错 |
| 修缺陷 | 兼容性 | 浏览器、分辨率、版本适配 | 前端 | 兼容、适配、分辨率 |
| UI 原型 | 过滤条件 | 新增或调整筛选控件 | 前端 | 新增下拉框、复选框 |
| UI 原型 | 表单字段 | 新增或修改表单字段 | 前端 | 新增字段、改标签 |
| UI 原型 | 表格列/按钮 | 新增列、按钮或调整布局 | 前端 | 新增列、新增按钮 |
| UI 原型 | 弹窗/对话框 | 新增或修改弹窗视觉 | 前端 | 新增弹窗、改对话框 |

判定时用需求原话里的动作词，但不要只靠关键词硬套：「加一个导出按钮」表面是加按钮，实际动作是接口调用；「加个字段」可能只是展示（改现有），也可能是计算（加逻辑），取决于值从哪来。

### 第三步：多标签与主动作优先级

一条需求可以同时有多个动作。规则是：1 个主动作 + 0 到 N 个关联动作。

主动作判定优先级：加模块 > 加菜单 > 改现有 > 加逻辑 > 加按钮 > 修缺陷。缺陷修复是例外：只要本质是修缺陷，主动作就取修缺陷，不被其他标签顶掉。

UI 原型永远作为关联动作，不担任主动作。需求里出现页面表单、表格列、按钮布局、弹窗视觉的新增或修改时，追加 `UI原型.{类型}` 关联标签，由需求专家在分析文档里补对应章节。

公共检查项（操作日志、权限、二次确认）不单独作为动作标签，由主动作专家与关联专家共用同一结论，不重复产出。

### 第四步：判规模

规模与动作正交，但受跨层影响：

- 小需求：改动文件不超过 3 个，且单层改动，不涉及数据层与核心层。
- 大需求：改动文件超过 3 个，或跨层，或涉及表结构、外部契约、编译产物。
- 业务方案确认：业务规则或数据口径待定，标 PENDING，等人决策。

跨层未知量不得按最小面算小：编译态产物、新接口、新字段、改表在未证实时，要外提为「分类判定点」，写清判定人和时间；或写明上调条件，例如「设计阶段确认需改数据层则升为大需求」。

已实现检测为「是」时，原分类假设可能被推翻，必须复核并记录偏差：原本按改动文件数判大，确认已实现后可能只是补差异，规模要下调。

### 第五步：输出路由卡

结论写成一张卡，至少包含：

| 字段 | 内容 |
|---|---|
| 功能类型 | 新增 / 修改 / 缺陷 / 排查 |
| 主动作 | 一级.二级 |
| 关联动作 | 0–N 个一级.二级 |
| 影响范围 | 仅前端 / 仅后端 / 前后端 / 数据层 |
| 难度 | 低 / 中 / 高 |
| 规模 | 小 / 大 / PENDING |
| 已实现检测 | 是（版本）/ 否 / PENDING（原因） |
| 主专家 | 承接主动作的专家 |
| 关联专家 | 按关联动作追加 |
| 待确认项 | 问题、判定人、阻塞级别 |

主专家按主动作映射：加模块、加菜单、加按钮、加逻辑、UI 原型归需求分析与设计；改现有归需求分析与开发；修缺陷归排查；改性能、改数据口径归设计与开发。涉及新增表、新增字段、本地表查询的，追加数据专家；需求类型为移植、补全、迁移的，追加对标专家；提示内容是公式的，追加公式溯源检查。

拿不准的项不硬判：写进待确认项，标明是阻塞还是非阻塞。无法明确判别时整卡标 PENDING，不猜一个看起来合理的结论。

## 示例

**示例一：查询页加导出按钮**

原话：「查询页加一个导出按钮，调导出接口，导出当前筛选结果。」

功能类型=新增；主动作=加按钮.接口调用；关联动作=加逻辑.过滤（导出要带当前筛选条件）；影响范围=前后端；规模=小（预计 2 个文件、单层）；主专家=需求分析；关联=设计；待确认=导出字段范围、是否限制条数。

**示例二：新增配置管理模块**

原话：「新增一个参数配置管理页面，能查、能改、能保存。」

功能类型=新增；主动作=加模块.配置模块；关联动作=加菜单.新页面、UI 原型.表格列；影响范围=前后端 + 数据层；规模=大（新页面 + 接口 + 表）；主专家=需求分析 + 设计；关联=开发、测试；待确认=配置是否持久化、是否需要审批。

**示例三：改现有过滤并追加原型**

原话：「委托查询加一个『仅当日有效』的筛选，页面加个复选框。」

功能类型=修改现有；主动作=加逻辑.过滤；关联动作=UI 原型.过滤条件；影响范围=前后端；规模=小；主专家=需求分析；关联=设计；待确认=过滤在前端还是后端、历史数据是否受影响。

**示例四：缺陷修复不被新增标签顶掉**

原话：「导出乱码，顺便把导出按钮加个提示。」

功能类型=缺陷；主动作=修缺陷.数据错误（乱码）；关联动作=加按钮.气泡提示；规模=小；主专家=排查；关联=开发。虽然出现了「加按钮」，主动作仍是修缺陷。

## 脚本

无脚本，纯语义判定。路由卡按上表字段输出，供下游直接读取；不额外定义 JSON schema，避免与调用方的产物结构冲突。

## 完成验证

- [ ] 功能类型已判定，修改现有类做过已实现检测。
- [ ] 主动作唯一，一级与二级都在分类表内。
- [ ] 关联动作数量与需求实际相符，UI 原型只作关联。
- [ ] 规模判定有文件数或层级证据；跨层未知量已外提。
- [ ] 路由卡包含主专家、关联专家、待确认项三栏。
- [ ] 拿不准的项标 PENDING，没有编造结论。

## 常见踩坑

- **按关键词硬套**：看到「加」就当加按钮，看到「优化」就当改性能。动作由「做了什么」决定，不由动词决定。
- **多标签没有主动作**：几个动作并列写，下游不知道该由谁主责。主动作只能有一个。
- **UI 原型当主动作**：原型类需求也需要一个实现型主动作，否则没有人落代码。
- **用「大概率」定小需求**：没有文件级证据就判小，后面必然返工。未知量外提，不硬压。
- **忽略已实现检测**：修改现有功能不做现状确认，方案会重复造轮子。
- **把排查当需求**：定位类诉求进需求链，会产出没有价值的设计文档。
- **待确认项没有归属**：写了 PENDING 却不说找谁、卡不卡后续，等于没写。
