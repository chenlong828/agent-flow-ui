## 适用场景

你接到的是伪代码层的改码任务，既包括落笔写，也包括把写完的东西送进机器与人工两道复核并交出契约。本技能覆盖两个栈的同一类工作：UFT 栈（UFR 同构，走同一套流程）与 ARES 栈。两者在输入契约、审核顺序与纪律上一致，差异集中在文件结构、入口、分层与宏体系、资源类型和审核条目来源。正文先给共同骨架，再用对照表摊开差异；不要因为两边长得像就套用对方的写法。

产物有四类：函数壳、函数体、导出后的 cpp、ARES 的资源文件。UFT 侧另有组件元数据查询与编译报错回溯两个入口，ARES 侧没有组件元数据，这一不对称要在动手前认清。

一次调用只走一个 mode：`encode` 产出改动，`review` 只审不改。混在一次调用里会同时污染契约与落盘结果，所以 mode 必须由调用方给定。

不做业务功能设计，不编排 L2、L3 与回退，不改规则库，也不替调用方拆任务。规则只引条目号不抄条文，条文正文在知识库正文件里，这里给的是取用路径与判定顺序。

触发词：伪代码、XML 壳、函数体、宏、事务、遍历、索引、获取记录、结果集、错误处理、字典、变量声明、入参出参、底层函数、标准字段、错误号、基础数据、表结构、打包解包、虚服务。

不适用：只做业务方案不落代码；只改普通配置文件；只做需求拆解或影响面分析；只查条文不改码。

## 执行步骤

### 第一步：确认 mode、栈与必填项

| mode | 判据 | 主要产出字段 |
|---|---|---|
| `encode` | 本次要写或改文件 | `modified_files`、`precheck`、`rules_cited` |
| `review` | 本次只审已经改好的文件 | `l0_status`、`l0_report_ref`、`l1_items`、`coverage_ref` |

mode 必须由调用方显式给出。没给就不分流、不落盘、不构造契约，直接要；不要从任务措辞里猜。做法是先确认 mode，再确认栈，再检查必填项；只有缺改动对象、待审文件，或规则库与快照读不到时，才把缺项写进 `pending_input`，其余字段留空等待。反例是拿到一段描述就直接产出完整契约，把「没给 mode」和「给错 mode」混成同一件事。

栈也由调用方点明。点不明时按产物特征判：出现 ARES 专有标记或资源文件后缀的走 ARES，其余走 UFT，交界处宁可先问一句。判错要整轮重读知识件、重引条目号，比问一句贵。

### 第二步：认栈对照

| 对照项 | UFT 与 UFR | ARES |
|---|---|---|
| 文件结构与标记 | 服务壳加代码段；标记族为 SVC、PCS、FNC、DTY、SMAC、UMAC、MUP、IDX、MARK、CONC、SAFE | 服务壳加代码段与资源文件；标记族为 ARES_XML、SVC、FNC、SQL、SAFE、CTRQ、BD、TBL；基础数据与表结构是独立后缀 |
| 知识位置与入口 | 语法、惯例、项目规则三组；接口族写法在族库的规格与实现两件 | 语法、SQL 与结果集、虚服务与分层、资源修改、质量门禁与差异表 |
| 编译与发布 | 导出 cpp 走映射件；编译报错有回溯件可回到伪代码定位 | 导出 cpp 走映射件；没有独立回溯件，按映射件与差异表处理，结论不确定时写进缺项 |
| 审核要点 | 预检十五条；红线按 SVC、PCS、FNC、SAFE、CONC 族取；段 B 判 cpp 生成条目 | 预检十条；红线按 ARES_XML、SQL、SAFE、CTRQ、BD、TBL 取；段 B 判 cpp 生成与 A 类条目，骨架态只跑通用子集 |

这张表只用来认清差异，不替代写法件：改哪个栈就只读哪个栈的写法件。反例是拿 UFT 的代码段标签、内部参数与获取记录宏去写 ARES。

### 第三步：圈定要读的领域文件

单次任务最多打开四个领域文件，红线预检占一个名额。顺序固定：先读红线预检与 L1 口径作为第一跳；再按「改什么」命中一行，只读点名标题到下一个同级标题；需要第二篇时再开，仍计入名额。改已有函数体时直接命中函数体那一行，不先打开壳层件。语法总纲只在调用层次或基本格式不清楚时占名额，不与函数体那篇叠加通读。反例是为了看全一点把整本语法读完，超预算还把注意力摊薄。

UFT 侧多一张功能类型分流表：查询、申报、回报、撤单、数据导出分别归通用查询族、委托下达族、回报族、委托撤销族、数据导出族，族实现未建时读暂存卡；加载初始化、定时批处理、参数维护、通信读暂存卡并叠加增量要点。族实现按契约编号覆盖比对通过后，该行改指族库、暂存卡撤销。ARES 侧没有这张表，按「改什么」行直接命中 SQL 与结果集、虚服务与分层、资源修改三组。

### 第四步：定放置

放置按三问走：先问校验什么、有无顺序约束，来源是上游规格或服务入口单；再问放哪一层、哪个位置，查放置模式总表；最后问落到哪个函数、哪个锚点，由修改规划环节实读源码后定。改码者不自行发明校验规则。

| 校验性质 | 放置位置 | 依据 |
|---|---|---|
| 参数格式与合法性 | 流程函数首段集中校验 | 服务层不承载校验 |
| 可复用的单对象业务校验 | 原子服务层，供多入口复用 | 改共享组件须列全部调用方 |
| 流程性业务规则与顺序约束 | 流程函数段，按业务顺序校验 | 顺序约束来自上游 |
| 编排与路由 | 服务层，只调函数 | 服务层不含分支式业务判断 |
| 因子计算 | 因子层 | 禁止记录增删改、关联关系与事务宏 |

反例有两类：把必填校验写进服务层，每个入口各写一遍；在因子层写事务与插入记录，把纯计算层拖成写库层。ARES 侧同表照用，但要过一层虚服务：调用 UFT 功能、柜台接口与总线，走虚服务与分层调用规则，判据是调用矩阵与调用链示例，不是宏名相似。

### 第五步：动笔

顺序先壳后体，体内依次是变量与入出参、宏、报错与日志、注释。

字段名的判据是查得到标准字段：入参与出参必须先过标准字段查询，非标准字段只能进内部参数且五属性齐全；反例是凭印象自造字段名，审核时连错误号都对不上。字典与枚举的判据是值域可查，按编号、中文名或枚举值反查，禁止把裸数字写进分支。函数签名与宏都按查得到的清单选：签名看参数方向，宏看选优单表，再回标记清单核细节。

报错返回的判据是每个失败分支都有错误号与日志，错误号来自错误号索引。UFT 侧改到事务、加锁或共享表更新时，先核对锁序基线，再按先父后子、方向一致、指令表先行的顺序写表更新。批量提交按经验值分批，事务配在遍历宏之外，循环嵌套不超过三层。同步调用必须显式配超时，常用 120000 毫秒，低于 60000 毫秒要给理由；不配即落系统默认，高负载时拖住调用方。参数读侧转数值前判空，空串直接转换会崩溃；写侧保证不了读取方健壮时，在规格里标注取值域。代码段里的宏标记与逻辑与符号必须转义，裸写会被当成标签。存在校验、范围校验、包含性校验、事务配对、条件遍历拆分、批量容错循环六类模板由渲染脚本产出，不许手抄。

ARES 侧改基础数据与表结构各有修改约束清单，改前逐章核对；表结构变化还要看生命周期与增量生成方式。

### 第六步：审核

审核分 L0 与 L1 两道，两道都过才算写法规范通过，只过一道不得宣称通过。L0 由检查器执行，通常经统一校验脚本按任务目录与卡号调用，也可直接对文件或目录跑栈对应的检查器。L0 通过指已挂检查器的 errors 为零，不等于红线全过，没被覆盖清单覆盖的红线要靠 L1 补。L1 核规则库里的 red 条目，每条给 PASS、FAIL 或 N.A.，对照快照件。

| L0 状态 | L1 范围 |
|---|---|
| `passed` | 只核覆盖清单未覆盖的 red |
| `failed` 或 `not_run` | 核全部 red，仍要完成 L1 填写 |

不得因为 L0 没过就不填 L1，也不得把 L0 的失败塞进 `pending_input`：后者只装缺对象、缺文件、缺规则库或快照这类没法开工的情况，`l0_status` 如实写 `failed` 或 `not_run`。ARES 资源改动有专项：基础数据走 BD 系列，表结构走 TBL 系列，适配与否由后缀映射判定，L0 必须真跑。段 B 管导出 cpp 之后的形态，先读 cpp 映射件，再按 cpp 生成类条目判定；ARES 段 B 在骨架态只执行声明的通用子集，不声称覆盖全部条目。

### 第七步：交契约与落盘

| 字段 | 何时有 | 内容 |
|---|---|---|
| `mode` | 总能回 | 与输入 mode 相同 |
| `modified_files`、`precheck`、`rules_cited` | encode 且无缺项 | 改过的文件、条目判定、条目号与规则库版本 |
| `l0_status` | review 且无缺项 | `passed`、`failed` 或 `not_run` |
| `l0_report_ref`、`coverage_ref` | L0 已跑 | 报告路径、覆盖清单路径与生成时间 |
| `l1_items` | review 且无缺项 | 条目号与三项判定之一 |
| `pending_input` | 总能回 | 缺项列表，没有则空数组 |

有 `output_path` 时以落盘脚本退出码为零为完成条件，落到调用方指定位置；没有时只交契约 JSON，不自行找目录写文件。一次调用只落一份结果，契约只写条目号不抄条文。

### 第八步：规则库纪律

快照与覆盖清单由生成脚本重建，禁止手改。规则库条目或版本变更后先重建快照，再跑四源对账，带陈旧快照进审核会被拦下；对账退出码必须为零，不为零说明规则、快照、覆盖清单与检查器已不一致，要继续查而不是绕过。

## 示例

**例一：新增字段（UFT，委托下达）**

需求是在委托下达报文里增加委托价格。先做标准字段确认，查得到就用标准名，查不到才考虑内部参数。再读壳层件，判断加在入参还是出参，参数节点成对补齐。然后按变量类别加声明，按选优单表挑传输宏，确认报文内转义，最后给失败分支补错误号与日志。反例是不查标准字段自造字段名，或在代码段里裸写宏标记，编译期才暴露解析失败。

**例二：改判断分支（UFT，参数维护）**

原逻辑是数量为负就报错，新要求是允许零、拒绝负数与非数字。判据是分支要穷尽：大于零、等于零、小于零、含非法字符四种都要有出口，参数读侧先判空再转数值。做法是改成四分支：大于零走正常流程，等于零走零值分支并继续后续校验，小于零报既有错误号，非法字符报格式错且在转换前拦下；日志只在最外层记一次。反例是只加一句「不等于零才报错」，非法字符落到转换函数，进程崩溃。

**例三：跨栈移植（UFT 查询改写为 ARES）**

原实现按索引条件遍历，再逐条获取记录。移植第一步不是换宏名，而是换范式：目标栈首选 SQL 与结果集写法，代码段标签、内部参数与获取记录宏都不是 ARES 首选。做法是读目标栈 SQL 与结果集件，重点四节：安全、空值、事务、多库；把遍历改写成带条件的查询；空值判断按判定选型表选函数；结果集释放责任按生命周期归属表落定；分层放置按调用矩阵确认。反例是逐个替换看起来对应的宏名就宣称移植完成，参数顺序与生命周期全没对上。

| 模板渲染、段 B 审核 | `render_code_patch.py`、`cpp_review.py` | UFT |
| 标准字段、错误号、字典、头文件签名、功能号与调用链 | `query_stdfield.py`、`query_errno.py`、`query_dict.py`、`query_header.py`、`query_service_index.py` | 两个栈 |

## 完成验证

- [ ] mode 与栈明确，一次调用只走一条路径；领域文件不超过四个，红线预检占一个名额。
- [ ] 放置按三问定到层与锚点，没有把校验写进服务层，也没有把事务写进因子层。
- [ ] 字段名、字典常量、函数参数都经过查询核对。
- [ ] 每个失败分支有错误号与日志，同步调用配超时，参数转换前判空。
- [ ] 事务与锁序按基线核对，表更新顺序与批量提交边界符合约定。
- [ ] 模板由渲染脚本产出，没有手抄。
- [ ] 审核两道都跑过，L1 范围与 L0 状态匹配，缺项字段只装缺项。
- [ ] 规则只引条目号，快照与覆盖清单未手改，对账退出码为零；有 `output_path` 时落盘成功。
- [ ] ARES 资源改动跑了 BD 或 TBL 系列 L0。

## 常见踩坑

- **没有 mode 就开工**。判据是 mode 必填且由调用方给；做法是停下来要 mode；反例是先产出看起来完整的契约，调用方还得倒推走了哪条路。
- **把 L0 通过说成审核通过**。判据是两道都过才算通过；做法是明确写出 L1 核对范围；反例是只贴一句 errors 为零就宣布通过。
- **L0 没过就不填 L1**。判据是 `failed` 与 `not_run` 都要核全部 red；做法是照表填 `l1_items`；反例是交一份只有 `l0_status` 的契约。
- **把 L0 失败写进 `pending_input`**。判据是缺项字段只装没法开工的情况；做法是把失败记在 `l0_status` 与报告路径上；反例是写「linter 没过」，下游无法区分是缺材料还是代码有问题。
- **跨栈照搬写法**。判据是目标栈的首选范式；做法是先读目标栈写法件再动笔；反例是把代码段标签、内部参数与获取记录宏直接搬到 ARES 侧。
- **凭记忆写字段名与错误号**。判据是查得到才算数；做法是逐个过查询工具；反例是审核时才发现字段不存在，整段重写。
- **手改快照或覆盖清单**。判据是这两份文件只由生成脚本写；做法是重新生成；反例是为了让对账变绿而改数据，把失真一路带进后续审核。
- **把 ARES 资源当非伪代码跳过 L0**。判据是后缀映射决定适用系列；做法是真跑检查器；反例是直接写 `passed`。
- **同步调用不配超时**。判据是同步调用必须有显式超时；做法是按常用值配并写明理由；反例是留空走默认，对端变慢时调用方被拖住。
