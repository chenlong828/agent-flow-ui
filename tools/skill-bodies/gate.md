## 适用场景

你是某个阶段的评审方，上游刚交付一批产物，你要判定它能不能进入下一阶段。门控不是打分，是放行判定：只要有一条强制约束不满足，就不放行，没有灰色地带。

本技能承载通用门控契约：双层判定、评审纪律、问题清单格式、置信锚、状态管控。各阶段具体查哪些文件、哪些约束，由评审角色定义，本技能不复制清单。

触发词：阶段门控、评审、放行、打回、review-issues、交付物审核、准出。

不适用：代码 diff 评审（走多 persona 代码评审）；存量代码巡检（走代码体检）；自评替代独立评审。

## 执行步骤

### 第一步：确认门控对象

先明确四件事：评审哪个阶段、评审哪些文件、依据哪份约束、评审方是谁。四件事缺一件就停，不能凭印象开审。

七阶段流水线与评审方：

| 阶段 | 上游角色 | 交付物 | 评审方 |
|---|---|---|---|
| 需求分析 | 需求分析 | 分析、任务、现状确认、范围边界 | 需求评审 |
| 方案设计 | 设计 | 任务单、方案计划、测试计划 | 设计评审 |
| 开发实现 | 开发 | 变更说明、代码、文件清单 | 开发评审 |
| 集成验证 | 集成 | 集成报告 | 集成评审 |
| 测试验证 | 测试 | 测试报告、缺陷清单 | 测试评审 |
| 发布 | 发布 | 发布说明、部署说明 | 发布评审 |
| 复盘 | 复盘 | 复盘报告、经验条目 | 无（不设门控） |

评审方只读被评审阶段的产物与既有问题清单，不读其他阶段的过程记录。跨阶段阅读会引入无关信息，也会让门控失去独立性。

### 第二步：第一层，确定性规则

逐项核对强制约束，命中即失败，不进入第二层。典型检查项：

- 现状确认：修改现有功能或缺陷类需求，是否先确认了现状；降级为代码扫描的，是否有用户确认记录。
- 同步一致性：代码与设计是否同步；改了接口是否更新契约；改了表是否更新结构说明。
- 测试留痕：测试计划、测试记录、缺陷记录是否齐；三岗自测是否各自有报告。
- 日志与可追溯：关键操作是否有日志；评审结论是否引用到文件与行号。
- 设计与任务对应：任务单是否覆盖全部需求点；需求点是否都有承接任务。
- 时间与时区：时间字段、时区标注是否符合约定。

以当前阶段实际适用的约束清单为准，不把别的阶段的检查项硬套过来。任何一条不通过，直接判未通过，写清是哪一条、位置在哪。

### 第三步：第二层，可用性判断

第一层全过后，判断下游能不能直接用：

| 维度 | 问什么 |
|---|---|
| 可实现性 | 方案落到代码是否有障碍，依赖是否已确认 |
| 覆盖完备性 | 任务是否覆盖全部需求点，有无遗漏或超出范围 |
| 接口与数据一致性 | 入参、出参、字段、口径是否前后一致 |
| 可测性 | 验收标准是否可判定，断言是否有锚点 |

结论用离散置信锚：100（确定可用）、75（基本可用，有非阻塞问题）、50（存疑，需补充）、25（大概率不可用）、0（不可用）。不用连续分数，也不写「大概没问题」。

### 第四步：守评审纪律

| 纪律 | 要求 |
|---|---|
| 只读不写 | 除问题清单外不落任何文件；不改上游产物 |
| 证据引用 | 每条结论给位置：文档到节或段，代码到文件与行号 |
| 身份标注 | 写明评审方角色、评审对象、评审时间 |
| 范围约束 | 只读被评审阶段产物与既有问题清单 |
| 独立评审 | 评审未执行等于门控未通过，禁止用自评替代 |
| 参考意见 | 建议类内容标「非约束性」，上游可自主决定是否采纳 |

评审方不执行需求分析、设计、开发、测试的具体工作；发现上游错误时，只记录并打回，不替上游改。

### 第五步：输出结论

通过：直接返回结论，不写文件。内容包含评审结果、评审对象、约束逐项结果、可用性简述。

未通过：在被评审方产出目录写问题清单，文件名带时间戳。格式：

```markdown
# 评审问题清单

- 评审方角色：
- 评审日期：
- 评审上游：

## 问题清单

1. [Status: Open] 问题描述（引用节/段或 文件路径:行号）

## 参考意见（非约束性）

- 建议内容
```

每条问题必须能定位到具体位置，不能写「文档不完整」这类无法复核的结论。问题状态用 Open / Resolved 两态；上游修复后逐条回填，不全量重写。

### 第六步：状态管控

门控结论要落到流程状态：通过则推进阶段；未通过则阻塞，写清阻塞项、责任方、期望完成时间。待确认事项单独建表跟踪，不混在问题清单里。

下游发现上游错误时，按「记录 → 打回 → 上游修复 → 重新评审」处理，不自行绕过。绕过一次，后面每一层都不可信。

### 各阶段检查要点

| 阶段 | 第一层重点 | 第二层重点 |
|---|---|---|
| 需求分析 | 现状确认、范围边界、需求点编号 | 需求点是否可验收、边界是否清楚 |
| 方案设计 | 任务单与需求点对应、接口与表设计齐全 | 方案可实现、依赖已确认、测试计划可执行 |
| 开发实现 | 代码与设计同步、文件清单完整、自测报告齐 | 改动是否越界、异常与权限是否处理 |
| 集成验证 | 集成清单、接口联调记录 | 跨系统契约一致、失败可回滚 |
| 测试验证 | 用例与需求点映射、缺陷记录、回归范围 | 结论是否有证据、遗留问题是否可控 |
| 发布 | 发布说明、回滚方案、变更审批 | 发布窗口、监控与值班安排 |

表里是通用要点，具体项目还有本地约束。本地约束与通用约束同名时，以本地为准；拿不准时列出两份约束的差异，请项目负责人裁决，不自行取舍。

### 结论记录模板

```markdown
## 门控结论

- 阶段：
- 评审方：
- 评审时间：
- 第一层：通过 / 未通过（命中项：）
- 第二层：置信锚与理由
- 结论：通过 / 有条件通过 / 不通过
- 阻塞项与责任方：
- 复评时间：
```

结论记录与问题清单分开存放：结论进流程状态，问题进问题清单。两者用同一时间戳关联，便于追溯。

## 示例

**示例一：需求阶段打回**

上游交付分析文档，第一层检查发现「修改现有功能未做现状确认」，且没有降级说明。直接判未通过，写问题清单：位置在分析文档第 3 节；要求补现状确认或补用户确认的降级记录。不进入可用性判断。

**示例二：开发阶段有条件通过**

第一层全过。第二层发现接口出参少一个字段，但该字段不在本期验收范围。置信锚 75，结论「有条件通过」：允许进入集成，但必须在集成前补字段说明，并在问题清单记一条非阻塞问题。

**示例三：测试阶段驳回**

测试报告缺少缺陷复现步骤，断言只有自然语言描述。第一层「可测性」不通过，判未通过；要求补复现步骤与断言锚点，补齐后重新评审。

## 脚本

无脚本。门控结论与问题清单用 Markdown 表达；流程状态由编排层维护，本技能只给判定与依据。

## 完成验证

- [ ] 评审对象、依据约束、评审方三者明确。
- [ ] 第一层逐项核对，命中项已写明位置。
- [ ] 第一层未过时没有进入第二层。
- [ ] 第二层四个维度都有结论，置信锚为五档之一。
- [ ] 每条问题都有精准位置，状态为 Open / Resolved。
- [ ] 参考意见已标「非约束性」。
- [ ] 未通过时已写阻塞项与责任方。

## 常见踩坑

- **自评代替评审**：自己交的产物自己审，门控形同虚设。评审必须独立。
- **先看可用性再看规则**：规则已经命中还继续往下评，结论会自相矛盾。第一层是硬门槛。
- **问题没有位置**：写「文档不完整」无法复核，上游也不知道改哪。必须到节、段或行号。
- **评审方替上游改**：越权修改会让责任边界消失。只记录，不打补丁。
- **参考意见当强制**：把建议写成必须执行，上游失去决策空间。建议要标注非约束性。
- **置信锚用连续分**：87 分、92 分无法对齐，五档离散锚才有共识。
- **绕过门控赶进度**：一次绕过，后面所有阶段结论都不可信。
