## 适用场景

你手上有一个已经确定的代码改动——一个提交、一组变更函数或一份 diff——要在它送去代码审核之前，先圈出「改了这里，别处哪里会受影响」。产物是一份分层的影响面清单：受影响的业务入口、功能号、调用方、表与字段、对外契约与配置、同族可疑点，再加一份能直接派给测试的回归清单。每条都要带证据锚点，能被另一个人独立复核。

输入是预处理已产出的材料：变更函数列表、伪代码、反向调用链结果、覆盖结果、需求分组。它们一次产出，本技能只读，不重跑。

本技能只回答「改了这里，别处哪里受影响」，不判断改动对不对，不给修复方案，不做语义拆解，也不排期。

触发词：影响面分析、正向调用链、反向调用链、波及范围、回归范围、同族功能扫描、断链、影响面分级。

不适用：改动点还没确定（走需求分析）；只需定位入口不看波及（走入口定位）；只需读某功能现状（走现状检查）。

## 执行步骤

### 第一步：圈定改动点

判据：改动点是能被单独描述、单独验证的最小行为单元，通常是一段分支、一处赋值或一次签名变化，不是一个文件。

做法：逐个变更函数读 diff 或伪代码，把改动归入五类：分支增删、返回结构、入参或签名、跨模块调用、配置或 SQL；每条写清位置与改动前后行为，位置用仓库相对路径加行号，绝对路径不能用于版本比对。

反例：把「改了这个服务实现类」当成一个改动点；函数里常同时改了几处无关逻辑，波及面完全不同，合并后链路取证就对不上号。

### 第二步：正向调用链取证

判据：正向链是「从改动函数往下，数据最终落到哪里」，终点必须是可命名的出口：表字段、外部报文、返回结构、写入的文件或消息；给不出终点的属于断链。

做法：按调用栈逐跳记录，每跳给出可复核锚点，即相对路径加行号或脚本名加实测输出行，并注明是方法调用、跨仓编译期依赖、跨进程通道还是 SQL。遇分岔两条都记，典型是同一功能号既可转核心也可在本服务内处理，只写一条会低估联调范围。

反例：只写「查询走核心、不落本地表」，没写清哪一行发起、发给谁；这种描述无法复核，下游也判断不了要不要联调。

### 第三步：反向调用链与入口归属

判据：反向链回答「谁在调用这个改动函数」，作用是把技术改动翻译成业务入口；入口要落到功能点，即哪个菜单、哪个页签或按钮、哪个对外服务，只给服务名不算落到位。

做法：读预处理已产出的反向链与覆盖结果，按受影响入口、未追到的入口、覆盖分组逐条落地。入口的权威来源是本次取证结果与知识图谱索引，不是任务单转述的服务名；定位先用功能号或服务名在索引里直定，再顺调用链走到代码，索引未命中按未命中类别定性，不转全库搜索兜底。

反例：把任务单转述的服务名当入口，或把 0 命中当作「无影响」；前者未经链路验证，后者只说明静态图没连上，两种都会漏掉真实入口。

### 第四步：补齐静态调用图看不见的引用

判据：函数只要是被「按名字找出来」调用的，静态调用图就看不到这条边。典型四类：其他仓库的编译期符号引用、事件或消息订阅方、定时任务按登记的类名或方法名发起、反射或字符串拼接调用。

做法：四类各扫一遍。符号引用按完整类名或方法签名跨仓检索，结果按仓库分组，不只扫改动所在的仓；事件按事件名查发布方与订阅方两个方向，只查一半会漏掉「本仓发、别处收」；定时任务按任务编码、类名、方法名三种写法各查一遍。扫不到不是结论，写明检索式与范围才是结论。

反例：改了一个批处理入口，反向链 0 命中就判定只影响手动触发的页面；实际调度配置按任务编码登记了它，日初自动跑，漏掉就是线上事故。

### 第五步：表字段与数据影响

判据：只要改动点读了或写了表字段，或改变了某个值的口径（单位、精度、枚举取值、空值语义），就存在数据影响，与有没有改 DDL 无关。

做法：逐表逐字段列出表名、字段名、读写方向、口径是否变化。字段是否存在以表设计文件为准，不以代码里的字符串为准；方言覆盖、对象注册、数据访问层候选各查一次，缺方言或缺注册按告警记录，再由本需求是否真改这张表决定严重度；口径变化要追到所有读取方，包括页面、导出、报表、下游服务。新建表先完成对象注册再交付。

反例：字段从整数改成小数就认为「代码已自动适配」；按整数截断的读取方不会报错，只会静默丢精度。

### 第六步：契约、配置与菜单影响

判据：契约看跨进程或跨仓库的接口定义有没有变；配置看有没有按名字生效的登记项要跟着改；菜单看用户能不能看到、能不能点到。

做法：契约侧核对接口声明、入参出参结构、报文字段、返回码与外部通道字段对照。同一份配置在多个仓库各有一份副本时逐份列出，漏改的那份会在部署后生效；菜单侧核对路由到功能号的映射、编号是否被占用、开通脚本是否要同步，编号这类假设必须代码侧扫描加脚本侧登记双侧核验，只有一侧可查就标待确认。导出、批量、异步等旁路入口单独列，它们常不走页面那条接口。

反例：只改一份权限配置文件就认为映射已更新，而同一份文件在业务仓有内嵌副本、集成部署仓的模板目录还有一份，任缺一处上线后行为都不一致。只写一个功能号同样会漏：一个菜单路由常映射多个功能号，分别对应不同页签与按钮，漏掉的往往是权限或导出这类不常点的入口。

### 第七步：断链标注与证据锚点

判据：每跳要么有锚点，要么明确标为断链，没有第三种状态。锚点固定写成「仓库相对路径:行号」或「脚本名加实测输出行」，状态只有实测可取、断链缺口、未验证三种。

做法：断链处写清三件事：断在哪一跳、缺的是哪个功能号哪一层、按什么方式补齐（由谁提供、登记到哪张追踪表）。仓库未检出、环境不可达、索引未覆盖都属断链成因，如实写「未取证」合规，凭知识库文字补一个看似合理的路径不合规。产物重跑时按字段保留性合并，不整文件覆写，否则会抹掉其他环节已写入的字段。

反例：断链处留空或写「详见核心侧文档」，下游拿不到可用信息，缺口不会被受理。把另一个业务动作的样本拼进本链路凑端到端更糟：两个动作的锚点拼接会产出看似完整实则错误的链路，评审会判为伪造证据。

### 第八步：影响面分级

判据：分级看三件事，取最严重的一项定级，与改动行数无关。

| 级别 | 判据 | 处置 |
|---|---|---|
| P0 | 涉及记账、资金、持仓、费用口径；或对外契约字段语义变化；或跨仓公共签名破坏性变更 | 人工确认后才能进开发；回归全覆盖并含历史数据核对 |
| P1 | 影响多入口或多仓但口径与契约兼容；或双边业务只改了一侧 | 人工确认受影响入口；回归按入口逐条列出 |
| P2 | 单入口单仓，口径与契约均不变，仅展示或内部组装调整 | 常规回归；抽检直接入口与同族功能 |

做法：定级先问三问：有没有动到钱和量；有没有动到别的系统能看到的字段；有没有动到别人也在用的公共符号。有一个答「是」就不是 P2。分级结论要写理由，理由指向具体锚点，不写「风险较高」这类空话。

反例：因为改动只有三行就定成 P2；改动行数与影响面无关，公共基座改一行签名可以让多个仓库同时编译不过。

### 第九步：回归清单与落盘

判据：回归清单是影响面清单的可执行投影，每条都能被测试直接执行，并能追溯到某个改动点；不可执行、不可追溯的条目不算完成。

做法：按四组组织：直接入口（菜单、页签、按钮、对外服务）、同族功能（同模块同能力的兄弟入口，逐个结论为需同步修、无问题、豁免）、旁路入口（导出、批量、异步、定时任务）、数据与契约核对（历史数据、方言、报文字段）。同族扫描要收敛，用三个条件取交集：同一功能能力下的兄弟入口、操作用到同一批表、写入同一个组件；交集之外不扫，全目录铺开会烧光上下文却给不出结论。

反例：回归清单写成「回归相关功能」，既不可执行也不可核对，等价于没写。

## 示例

**示例一：返回结构新增字段（页面仓与导出）**

输入：服务仓查询服务的返回组装逻辑新增对手方代码字段，表里本就有这一列，之前没透出。

影响面清单：反向链落到页面查询与导出两个入口，导出走服务方法直调；表字段无变更；出参新增字段，外部报文未变；菜单与配置无变更；同族扫描发现另一方向的同名查询有同款组装逻辑，需确认是否同步；分级 P2；回归该列展示、导出、空值与排序筛选。

**示例二：公共基座方法签名变更（跨仓）**

输入：服务仓在公共基座模块给通道适配类的方法增加超时参数，同仓调用点已同步修改。

影响面清单：反向链只覆盖本仓，跨仓引用靠符号检索补齐，检索式用完整类名，命中分布在四个仓；契约侧属编译期依赖变化而非运行时接口变化，外部无感知；表无影响；分级 P0，理由是公共符号破坏性变更，任一引用仓未同步都编译失败；回归全部引用点的调用行为、超时取值、分页参数。

**示例三：表字段类型与单位变更（数据口径）**

输入：某业务表的金额字段由整数改为定点小数，单位从元改成万元。

影响面清单：表设计文件、各方言建表脚本、对象注册、数据访问层四处都要改，缺方言按告警记录并注明是否本需求必需；读取方包括页面、导出、报表、下游服务，逐个确认换算发生在哪层；历史数据是否迁移单列一项；分级 P0，理由是口径变化影响对账；回归新写入精度、历史数据读取、导出金额、各方言取值。

**示例四：定时任务与菜单配置（反向链零命中）**

输入：改了一个按任务编码登记的批处理函数，调用图里没有调用方；另新增一个页签，路由复用已有路由。

影响面清单：按任务编码、类名、方法名三种写法在调度配置里检索，确认每日初被调起，属真实受影响入口，不能记「无影响」；菜单侧路由到功能号是一对多，新页签对应其中一个号，需逐份核对副本；菜单编号只有代码侧可查、脚本侧未检出，标待确认；分级 P1；回归日初批处理结果、新页签展示、同路由下其他页签不受影响。

## 脚本

本技能不自带脚本。链路与覆盖数据由预处理产出，本技能只读不重跑。可用脚本分三类：

| 脚本 | 用途 | 使用边界 |
|---|---|---|
| 反向调用链与覆盖脚本 | 产出受影响入口、未追到的入口、覆盖分组 | 由预处理执行；本技能只读产物 |
| 影响面落盘脚本 | 按字段把结果合并进影响面产物 | 只能按字段合并，不能整文件覆写，否则会丢其他环节写入的字段 |
| 产物校验脚本 | 校验输出完整性 | 收尾统一跑一次，不逐个文件手工核对 |

输出字段固定，未取到的值留空并标缺口，不填猜测值：

```json
{
  "impact_scope": {
    "changed_points": [{"anchor": "相对路径:行号", "kind": "branch|return|signature|call|sql"}],
    "forward_chain": [{"hop": 1, "anchor": "", "status": "verified|broken|unverified"}],
    "reverse_entries": {"ls_entries": [], "ls_entries_count": 0, "gaps": [], "gaps_count": 0},
    "symbol_refs": [{"repo": "", "anchor": "", "kind": "compile|event|schedule|reflect"}],
    "tables": [{"table": "", "field": "", "rw": "read|write", "caliber_changed": false}],
    "configs": [{"file": "", "repo": "", "kind": "menu|permission|dict|sql", "status": "changed|unchanged|pending"}],
    "siblings": [{"entry": "", "verdict": "needs_fix|no_issue|exempted", "reason": ""}],
    "regression": {"direct": [], "siblings": [], "bypass": [], "data_and_contract": []}
  }
}
```

脚本源码不在本技能的阅读范围内，用法以本文与脚本自带帮助为准。

## 完成验证

- [ ] 每个改动点都有锚点，且写清了改动前后的行为。
- [ ] 正向链每跳都有锚点或明确标为断链，断链写清缺什么、由谁补。
- [ ] 反向链入口来自本次取证结果与索引，不是任务单里的转述。
- [ ] 符号引用、事件订阅、定时任务、反射四类盲区都扫过，并写明检索式与范围。
- [ ] 表与字段的读写方向和口径变化都列了，读取方清单完整。
- [ ] 契约、配置、菜单三类影响都判过，多副本配置逐份列出。
- [ ] 同族扫描用三条件交集收敛，每个候选都有结论与理由。
- [ ] 分级理由指向具体锚点，回归清单四组齐全且可执行。
- [ ] 落盘产物字段完整，缺口清单有值。

## 常见踩坑

- **反向链零命中就判无影响**：静态调用图看不到按名字发起的调用。判据是四类盲区都扫过才算排除；做法是查符号引用、事件订阅、调度配置、反射入口；反例是只看调用图就写「无影响」。
- **拿任务单里的服务入口当结论**：转述的服务名未经链路验证。判据是入口必须出现在本次取证结果里；做法是索引直定加调用链验证；反例是把转述写进清单充当证据。
- **把逻辑分层当成调用帧**：适配层是分层视图，不是运行时通道。判据是每跳能否指出实际调用点与客户端名；做法是按实际通道写到发送方法；反例是把适配层写成一跳。
- **把宽松命中当调用点**：按功能号检索时，宽松命中的常是入参出参类名。判据是命中行是否在调用语句里；做法是只采严格命中，宽松命中仅作弱证据；反例是把入参类名当成调用点。
- **只写路由不写子应用与组件**：同名路由在两个仓都存在，加载的是不同组件。判据是落点能否定位到组件文件；做法是写到子应用加组件路径加行号；反例是只写路由名，改错仓。
- **拼凑端到端链路**：把别的业务动作的锚点接进本链路，会得到看似完整实则错误的链路。判据是每跳是否属同一业务动作；做法是旁证与主链分开写并注明不属本链；反例是把两个动作的锚点接成一条链。
- **未检出就写「无变更」**：未检出只说明本机取不到证。判据是「无变更」是否有检索范围与依据；做法是写「未取证」并标待确认；反例是把环境问题写成结论。
- **整文件覆写影响面产物**：其他环节写入的字段会被抹掉。判据是重跑是否走按字段合并；做法是走合并脚本并核对结果；反例是覆写后下游缺字段。
