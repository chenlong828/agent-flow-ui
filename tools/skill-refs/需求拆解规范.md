# 需求拆解规范（scene=requirement）

> **本文是"把一段需求文本拆成需求本体"的方法学单源（2026-10-19 用户裁决：由 `02_需求LoopAgent/约束/需求拆解方法学.md` 直接迁入本包）**。RD-1 需求拆解专家与任意会话在此共享同一套规程；原 Agent 侧文件已改为桥接页指向本文。
> 适用：`scene=requirement`。执行模型＝独立会话（落盘件是唯一交接面）。
> 本场景**不做定位**：功能号/表/服务入口/流程名的定位归 `kg-locate`＋`source-asset`，不在本技能（见 §八）。

## 一、总则

1. **拆解对象与产出**：需求描述＋处理意见 → **四件**（①需求目标 ②需求价值 ③需求范围 ④客户实际操作场景）＋ **SVO 骨架**。
2. **步骤序**：⓪底图 → ①目标 → ②价值 → ③范围 → ④操作场景 → ⑤SVO → ⑥自检。
3. **三条红线**：
   - **只用户语言**：四件＋SVO 本体禁系统术语（功能号/表/服务入口/流程名/模块名）；架构细节只进 ⓪ 的 `system_context` 与底图节。
   - **不锚定系统现状**：先立需求本体完整性——用户要而系统没有的能力不得漏掉或就近硬套（实证教训 2026-10-18：RTGS 修改点错挂可卖计算链）。
   - **待确认显式**：拆解不了、语义存疑的点标"待确认"，不硬填、不猜。

## 二、步骤 ⓪：两类背景（前置）

### ⓪-a 系统认知底图

调度 `app-node` 系统认知，**通读 `PB2系统认知.md` 全件**（§一~§十一）：

| 侧 | 读什么 |
|---|---|
| 用户侧 | 产品定位/客群/角色地图/投资流程五模式/功能域全景 |
| 架构侧 | 系统组成/交易日数据循环/主备机制/节点接入 |

用途：定位本需求的**操作域**（谁的操作）、**流程模式**（五模式之一）、**所在链路形态**。

**落盘要求**（独立会话交接面）：`system_context` 必填——cognition_ref（认知件路径＋版本）/ actors（涉及角色）/ flow_mode（五模式或"不适用"）/ function_domain / chain_form（链路形态一句话）/ summary（2~3 句）。无对应项填"不适用"，整字段不可省略；底图不可用时 cognition_ref 照填路径、summary 注明不可读。

### ⓪-b 业务规则背景（条件触发）

底图回答"系统怎么做"，规则回答"**市场怎么规定**"。二者并列，都是背景输入。

| 项 | 内容 |
|---|---|
| 触发 | 需求涉及**业务规则本身**：结算方式／交收时点／市场差异（沪深北）／品种规则／费率／监管口径 |
| 不触发 | 纯系统功能交互、内部实现改造 → `applicable=false` ＋ `not_applicable_reason`，不做检索 |
| 检索 | `find_tool.py --type business_rules --keyword <词>`（递归全语料）；禁用 glob 全库找规则 |
| 定位辅助 | `ext-interfaces`（`route_external_query.py`／各子域 README 的「关键条款锚」直达行号） |
| 记录 | 每条：topic／rule_file／clause（条款号或行号）／verdict[一致\|补充\|冲突\|无规定]／note |

**用途只有两处，都是"界定"而非"改写"**：

| 用途 | 作用点 | 说明 |
|---|---|---|
| ① 界定需求范围 | 步骤 ③ | 某市场该品种是否具备需求前提 → 决定 in/out，理由须引规则锚点 |
| ② 校验操作场景 | 步骤 ④ | 场景在市场规则下是否可能发生 → 不可能则标待确认或退回 |

**红线**：

1. **不改写用户诉求**——规则与需求冲突时不自裁，两种取舍（如"排除该市场"vs"保留但实现方式不同"）都摆出，登记 W 项交人工；
2. **不引技术名词**——读完规则后产出中不得多出服务入口/表/字段/模块名，多出即越界；
3. **不抄规则原文**——只写结论＋锚点，避免双源漂移；
4. **不转交规则原文**——下游只拿范围/场景结论；需要规则细节的由自身调度 `ext-interfaces`。

> 同一品种沪深规则可能不同（如定向可转债：深市 T+0 RTGS／沪市 T+0 日终逐笔全额），**必须按市场分别取规则**，不可跨市场类比。


## 三、步骤 ①：需求目标

提炼**需求目标**——一段话说清"本需求要达成的业务目的"。

判据：可被需求原文直接支撑；不引入原文没有的目的；一段话内不出现实现方式。

## 四、步骤 ②：需求价值

用户视角提炼**需求价值**——为什么需要／解决什么问题／带来什么收益。

判据：价值主体是用户（角色可落到底图角色地图）；收益可从目标推出。

## 五、步骤 ③：需求范围

划定**包含项清单＋明确排除项清单**；**每个排除项必附理由**（不写理由的排除项视同未排除）。

## 六、步骤 ④：客户实际操作场景

逐条拆解：**用户角色＋业务场景＋用户操作＋预期**，并标类型：

| 类型 | 定义 |
|---|---|
| 正常 | 主流程成功路径 |
| 异常 | 拒绝/报错路径 |
| 边界 | 不支持/极限条件 |
| 待确认 | 能力未知——不硬填、不猜 |

判据：角色用底图角色地图的称谓；场景/操作/预期均为用户语言；预期写"用户看到什么"，不写"系统做什么"。

## 七、步骤 ⑤：SVO 骨架与双向覆盖校验

从目标/范围/操作场景提炼 **"要什么不说怎么做"** 的 SVO（四成分定义见 `references/01_核心定义与拆解规则.md`）。

**双向覆盖校验**：每个操作场景有 SVO、每条 SVO 有场景；处理意见逐条对照同规则（有对应，或写明"不产出理由"）。

## 八、与定位段的分工（requirement 场景专属边界）

| 事项 | 归谁 |
|---|---|
| 需求本体（四件＋SVO） | 本场景 |
| 功能号/服务名 → V 卡 | `kg-locate`（禁 grep/glob 盲扫，见其红线） |
| 服务入口 → 调用链 → 代码锚点 | `source-asset`（`trace_call_chain.py`，禁 grep/glob 盲扫） |
| 修改清单点/表/参数 | 需求拆解之后的契约转译段，不在本技能 |

**红线**：本场景产出里出现功能号、表名、服务入口名即视为**越界**——需求本体被系统现状锚定的典型症状；应退回重拆，把该信息留给定位段。

## 九、步骤 ⑥：自检落盘

按调用方卡片的"产出校验"清单逐项自检（校验清单单源＝调用方卡内输出契约，本文不复制）。

## 十、步骤→字段映射

| 步骤 | 机器件字段 | 人读件 |
|---|---|---|
| ⓪-a | `system_context`（必填） | 系统认知底图节 |
| ⓪-b | `business_rules_context`（必填；未触发放 `applicable=false`＋理由） | 业务规则背景节 |
| ① | `requirement_goal` | 需求目标节 |
| ② | `requirement_value` | 需求价值节 |
| ③ | `requirement_scope`（in[]/out[{item,reason}]） | 需求范围节 |
| ④ | `user_view[]` | 操作场景表 |
| ⑤ | `svo_list[]` | SVO 清单（无机器 ID） |
| ⑥ | 全件自检 | 全件自检 |

> 字段必填性/枚举/格式单源＝调用方的机器件 schema（RD-1＝`02_需求LoopAgent/schemas/e09/req_decomp.schema.json`）；本表只是步骤→字段的导航映射。
