# Skill 写作规格（逐条细化到可落笔）

> 上一版 `skills.md` 回答「有几条、拆几个文件」；本文回答「每一节写什么、多少字、reference 里放哪些小节、description 原文是什么」。每条卡片都可直接落成 `SKILL.md` + `references/`。

## 0. 全局写作规范

### 0.1 结构

- `SKILL.md` 无 YAML frontmatter；`description` 单独落 B1 字段，正文从 `## 适用场景` 开始。
- 固定七节，顺序不变：适用场景 / 执行步骤 / 示例 / 脚本 / 完成验证 / 常见踩坑 / 参考资料。
- 每节只写该节的事：步骤不写背景，踩坑不写步骤，示例不写规则。

### 0.2 字数预算（以正文 6 KB ≈ 2,000 汉字为基准）

| 节 | 占比 | 6 KB 技能 | 10 KB 技能 |
|---|---:|---:|---:|
| 适用场景 | 12% | ~240 字 | ~400 字 |
| 执行步骤 | 34% | ~680 字 | ~1,100 字 |
| 示例 | 18% | ~360 字 | ~600 字 |
| 脚本 | 5% | ~100 字 | ~160 字 |
| 完成验证 | 10% | ~200 字 | ~330 字 |
| 常见踩坑 | 16% | ~320 字 | ~530 字 |
| 参考资料 | 5% | ~100 字 | ~160 字 |

### 0.3 `description` 公式（≤400 字，目标 80–150 字）

```text
适用：<什么场景/什么时候用它>。触发：<3–6 个触发词>。不适用：<1–2 个负向边界>。
```

- 不写「本技能用于」这类空话；直接写判断条件。
- 触发词用顿号分隔，不超过 6 个，避免关键词堆砌。
- 「不适用」必须指向另一个技能或明确边界，不能写「其他场景」。

### 0.4 reference 规范

- 每个 reference ≤8 KB；h2 3–5 个；每个 h2 下 ≤2 KB。
- 只放三类内容：规则/清单（表格化）、判定树/对照（好例/坏例）、示例（输入→输出）。
- 不复制 `SKILL.md` 已有内容；正文用「见 references/01」一行带过。
- 不写内网地址、客户名、项目号；路径统一 `workspace:/`。

### 0.5 落笔顺序

先写「步骤」→ 再写「验证」→ 再补「踩坑」→ 最后写「适用场景/示例」。步骤与验证定不下来时，不要动笔写正文。

`检索 · P0 · 正文 6 KB · 3 文件 · 主用 exp-tx-req / exp-web-req`

- **description（约 115 字）**：适用：收到原始需求、缺陷单或一句话诉求，需要判断它属于哪类改动、走哪条工作流时。触发：需求分类、动作判定、加按钮、加逻辑、改现有、修缺陷。不适用：需求已拆到任务级、只需执行；或只需查代码现状。

## 适用场景

你手上是一段人话——缺陷描述、需求原话、或评审给的修改点——要把它变成能回指原文的事实锚，供入口定位、根因判断、用例断言共用。你不判根因、不定方案、不找代码入口；这些分别归排查、设计和代码现状技能。

拆完必须能回答四个问题：谁（S）、发生了什么（V）、对象是什么（O）、结果是什么状态（O_effect）。答不全就标 `pending_input`，不要用推断补齐。

触发：SVO、拆现象、拆需求、锚点齐备性。
不适用：已有结构化场景或用例；纯代码定位。

## 执行步骤

1. **抽 S（主体）**：系统、模块、单据、账户。粒度到「能定位」即可，不要写到表名。
2. **抽 V（行为/现象）**：显示、校验、提交、回滚、超时、丢失。用动词或状态词，不用评价词。
3. **抽 O（实体/字段）**：被操作或被观测的对象。优先用原文词，原文没有就用系统里的同义字段名，并标注来源。
4. **定 O_effect（影响态）**：错误值、缺失、延迟、重复、拒绝。必须是可观测状态，不是原因。
5. **补 attributes 并做齐备性检查**：时间、环境、频率、账号、版本。缺项写 `pending_input`，注明缺什么、找谁要。

产物是 JSON：`{S,V,O,O_effect,attributes,pending_input}`。每项带 `text_ref`，指回原文的句子或段落。

## 示例

输入：「柜台反映，客户做委托的时候，委托金额那一栏有时候显示 0，但实际是有钱的。」

输出：

- S：委托单（原文「委托」）
- V：显示（原文「显示 0」）
- O：委托金额（原文「委托金额那一栏」）
- O_effect：恒为 0 / 与实际可用资金不一致（原文「显示 0，但实际是有钱的」）
- attributes：柜台端、部分客户、偶发（原文「有时候」）
- pending_input：环境版本（缺）、复现账号（缺）

注意：`O_effect` 不写「资金计算错误」——那是判断，不是状态。

## 脚本

无脚本。输出 JSON 由调用方写入任务目录；字段名固定，不新增同义字段。

## 完成验证

- [ ] S/V/O/O_effect 四项齐全，且都有 `text_ref`。
- [ ] O_effect 是可观测状态，不含因果判断。
- [ ] 缺失项进入 `pending_input`，写明缺什么、找谁。
- [ ] 没有把方案、根因、代码位置写进产物。

## 常见踩坑

- **现象与判断混写**：把「显示 0」写成「金额计算错误」，下游会直接跳到根因。
- **O_effect 写成根因**：根因属于排查结论，不属于事实锚。
- **缺锚点硬往下走**：没有 `text_ref` 的项一律视为未确认，不得进入定位。
